# Changelog

All notable changes to OxiZ will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.3.3] - 2026-08-26

A soundness release. Issues [#44](https://github.com/cool-japan/oxiz/issues/44)-[#50](https://github.com/cool-japan/oxiz/issues/50) named seventeen `.smt2` files from the non-incremental SMT-LIB distribution, every one carrying `(set-info :status unsat)`. Fifteen were obtained and run against the 0.3.2 tree, and **all fifteen answered `sat`, most of them inside a second** — the worst class of SMT bug, and not a search-budget artifact. Eight independent soundness defects (plus one latency fix) came out of the diagnosis; none of the fifteen answers `sat` any more. Alongside that, three of this project's standing honest rejections became real support — recursive functions, a first-class `RoundingMode` sort, and algebraic-number witnesses for irrational roots — and the SAT engine picked up the pre-search "lucky" phase and the BVE wiring that [#35](https://github.com/cool-japan/oxiz/issues/35)/[#36](https://github.com/cool-japan/oxiz/issues/36) asked for.

### Breaking changes

OxiZ is pre-1.0; per Cargo's SemVer convention a `0.x` minor bump is the breaking-change signal.

- **`oxiz_core::smtlib::Command` gained a `DefineFunsRec(Vec<RecFunDecl>)` variant** (`oxiz-core/src/smtlib/parser/mod.rs:137`). The enum is not `#[non_exhaustive]`, so an exhaustive `match` over it stops compiling; that is deliberate, and the variant's own doc says why at length. A recursive definition is the *only* thing that constrains the symbol it defines — the parser registers the name as an ordinary declared function so call sites build a real `Apply`, and never expands the body (expansion would not terminate) — so a consumer whose `match` lets this command fall into a catch-all keeps every `(f x)` application and drops every constraint on `f`, silently solving a strictly weaker problem and turning `unsat` into `sat` with a meaningless model. A consumer that cannot solve recursive definitions must error or answer `unknown`. All three in-workspace consumers do: `oxiz-solver` solves it, `oxiz-spacer` returns `ChcCompError::Unsupported` (`chccomp.rs:96`), `oxiz-smtcomp` returns `BenchmarkStatus::Unknown` (`parallel.rs:398`).
- **`TermManager::mk_bv_concat` is replaced by `try_mk_bv_concat(&mut self, lhs, rhs) -> Result<TermId>`** (`oxiz-core/src/ast/manager/builder.rs:1235`). The infallible version defaulted an unresolvable operand's width to a fabricated `32` in release builds; a fabricated width is not cosmetic, because it interns a well-formed term at the wrong sort, which can flip a query between `sat` and `unsat`. The new function returns `OxizError::SortMismatchSimple` naming both operand sorts. `oxiz-py`'s `PyTermManager.mk_bv_concat` now raises `ValueError` on a non-BitVec operand; `oxiz-solver`'s `z3_compat::BV::concat` stays infallible to keep the Z3 C-API contract and, on error, interns at the correct sort computed from the wrapper's own tracked widths.
- **`SortKind::RoundingMode` and `Value::RoundingMode(RoundingMode)` are new variants** (`oxiz-core/src/sort/mod.rs:84`, `oxiz-core/src/model/mod.rs`), neither enum `#[non_exhaustive]`; `SortManager` gained a public `rounding_mode_sort: SortId` field and now eagerly interns four sorts in `new()` — `Bool`(0), `Int`(1), `Real`(2), `RoundingMode`(3) — so user sorts start at raw id 4 rather than 3. Code that hard-codes raw `SortId` numbers needs checking; code that dispatches on `SortKind` (as `ValueFactory::default_value` does) does not.
- **`oxiz_core::theories::combination::Theory` was rewritten into a trait that can actually be implemented**: it gained `core::fmt::Debug` as a supertrait and a required `assert_equality(a, b) -> bool`; `add_term` returns `bool` (did this theory claim the term); `check` takes `&mut TermManager`; `TheoryResult::Unsat` became the struct variant `Unsat { explanation: Vec<TermId> }` and a `Lemmas(Vec<TermId>)` variant was added; `NelsonOppen::add_equality` and `TheoryCombiner::add_equality` return `bool`. In the same layer `DatatypeAxiom`'s five name fields changed from `interner::Spur` to `String` (the axioms travel between two separate interners) and `axiom_to_term` returns `Option<TermId>`.
- **`SolverConfig` grew new public fields on both crates** — plain, non-`#[non_exhaustive]` structs, so downstream code constructing one by full struct literal (without `..Default::default()`) needs updating. `oxiz_sat::SolverConfig`: `enable_lucky_phase`, `enable_self_subsumption` (both `true` by default). `oxiz_solver::SolverConfig`: `enable_bve` (`false` except in `thorough`), `nonlinear_relaxation_engine` (`true`), `enable_model_blocking` (`true` except in `minimal`), `max_model_blocking_rounds` (64). `oxiz_solver::Statistics` gained `model_blocking_clauses`.
- **`NlDispatchResult::Sat` changed shape again**: `Sat(Box<Interpretation>)` → `Sat { witness: Box<Interpretation>, algebraic: FxHashMap<TermId, NlWitnessValue> }` (`oxiz-theories/src/nlsat.rs`). Exactly one of the two is ever populated — a nonlinear model is either wholly rational or carries algebraic values, never a mix of channels — and `witness_from_real_translator` is now all-or-nothing, returning `Interpretation::empty()` rather than a partial map if any variable lacks a rational value. Every match site in the workspace moved to `Sat { .. }`.
- **`TermManager::arena_stats()` and `TermManager::reset_arena()` are removed.** The `arena` feature and `oxiz-core/src/ast/arena.rs` still build, but `TermManager` no longer writes to the arena at all — see the intern-retention entry under "Fixed".

### Soundness fixes (wrong `sat` corrected)

- **Fifteen SMT-LIB benchmarks that OxiZ reported `sat` are unsatisfiable, and none of them reports `sat` any more.** The two QF_BV files in [#47](https://github.com/cool-japan/oxiz/issues/47) were never obtained, so **#47 stays unreproduced locally and is not claimed fixed**; the other fifteen (`storecomm_*` and the Rodin `smt8591958557635707797` from #44, three `ring_2exp*` from #45, `xs-08-20-3-2-4-5` / `xs-06-15-4-1-4-1` / `xs_8_13` from #46, the QF_ANIA `GrandProduct` case from #48, `jobshop4-2-2-2-4-4-11` from #49, `vhard7` from #50) all returned `sat` on 0.3.2. The corpus is competition data and is not vendored here, so the durable evidence is in-repo regression tests built from minimal repros that fail on the pre-fix code: 43 of them in `oxiz-solver/tests/{arith_diseq_soundness,array_store_extensionality,qf_nia_relaxation}.rs`, plus the in-module suites named below. Re-measured on the fixed tree, the files that were checked answer `unsat` (`storecomm_t3_np_sf_ni_00010_001.cvc`, `xs-08-20-3-2-4-5`, `jobshop4-2-2-2-4-4-11`, `smt8591958557635707797`, `ring_2exp8_3vars_2ite_unsat`) or an honest `unknown` (the QF_ANIA case, which is nonlinear integer arithmetic over arrays).
  - **This release does not claim all fifteen are now *decided*.** `xs_8_13` (QF_UFLIA) and `vhard7` (QF_UFIDL) run out of time rather than answer, and the two larger `ring_2exp*` files and `storecomm_t1_pp_nf_ni_00050_001` were last seen timing out as well. The search-performance work those need was deliberately deferred to a later release. A timeout is a refusal, not a verdict — what changed is that a wrong answer is no longer among the outcomes.
  - **A `let` wrapper blinded every assert-time pre-pass** (`oxiz-core/src/smtlib/parser/terms.rs:652`). The parser resolves `let` by substituting into `Parser::bindings` *before* parsing the body, then wrapped the already-expanded body in a `TermKind::Let` that bound nothing. `Let` is a genuine capture-avoiding binder everywhere else in the tree, so every pre-pass refused to descend through it: `eliminate_nonbool_ite`, `abstract_compound_bool_args`, `flatten_lookup_spines`, `purify_numeric_uf_args` and the quantified-model gate were all silently disabled for the whole assertion. Two formulas differing only by an *unused* `(let ((q 0)) …)` got different verdicts, one of them a wrong `sat`. The vacuous wrapper is gone; `TermManager::mk_let` is unchanged for programmatic construction. Covered by `arith_diseq_soundness.rs`'s `ite_uf_argument_is_refuted_through_an_unused_let_wrapper`, `compound_uf_argument_is_refuted_through_an_unused_let_wrapper`, `disequality_under_a_let_is_refuted` and their no-`let` twins.
  - **A numeric equality forced *false* constrained nothing** (`oxiz-solver/src/solver/encode.rs:1088`, `add_numeric_trichotomy` at `:1512`). `ArithSolver` has no `assert_neq` — a disequality is non-convex — and `TheoryManager::process_constraint`'s negative branch speaks only to EUF and BV, so a false-assigned numeric `Eq` left the LP free to give both sides the same value. The only rescue was a syntactic pre-pass that enumerated a handful of connectives, so an equality reachable only through `Xor`, an `Implies` antecedent, a nested `Eq` or a `let` was missed entirely. Every numeric equality atom now emits `(= a b) ∨ (a < b) ∨ (a > b)` at encode time, which is the one place every such atom must pass to get a SAT variable. The three-way form is load-bearing: the unguarded `(a < b) ∨ (a > b)` split would itself be unsound. Four overlapping walks (`add_arith_diseq_split`, `add_arith_trichotomy_clause`, `add_arith_eq_trichotomy`, and the never-called `add_arith_diseq_splits_for_sat_model`) were deleted in its favour — `encode.rs` is 86 lines *shorter*.
  - **A violated disequality was invisible to the model-refutation gate** (`oxiz-solver/src/solver/model_eval.rs:666`, consumed at `check_core.rs:491`). `combine_eq` deliberately answers `Undetermined` when two numeric operands evaluate equal, because a collision in the LP model is not by itself evidence — the tableau enforces disequalities by case-splitting, not by pinning distinct witnesses. The missing information is the trail polarity: if the core assigned `(= a b)` **false** and the model makes both sides equal, that is a definite refutation. Conservative by construction — both sides must evaluate to a definite number, and only `LBool::False` atoms count. Tests: `pigeonhole_over_disequalities_is_never_answered_sat`, `distinct_over_a_too_small_range_is_refuted`, with the sat control `pairwise_disequalities_stay_sat_when_the_range_is_wide_enough`.
  - **Lazy theory mode threw away assignments the SAT core had not undone** (`oxiz-solver/src/solver/theory_manager.rs:1764`). `on_backtrack` called `clear()` on the whole pending queue, discarding assignments made at or *below* the backtrack level — and `on_assignment` fires once per assignment, so they were never re-sent. `x = 2 ∧ y = x+1 ∧ y ≠ 3` came back `sat` in lazy mode while eager mode said `unsat`. The queue is now level-tagged (`Vec<(Lit, bool, u32)>`) and pruned with `retain(|&(_, _, lvl)| lvl <= level)`. In the same pass lazy mode gained the shadow trail (`assignment_trail`) it had never maintained, which re-enables the `final_check` rebuild backstop there; that half is a *completeness* fix — its symptom was `unknown`, not a wrong `sat`. The four `lazy_mode_*` tests in `arith_diseq_soundness.rs` run both modes and require agreement.
  - **A formula built only out of `store` never instantiated an array axiom** (`oxiz-solver/src/solver/encode/track_theory_vars.rs:273`). `has_array_ops` gates the entire array-axiom loop at `check_core.rs:420`, and its only *reachable* setter was the `Select` arm: `TermKind::Eq` routes non-Bool operands through `track_theory_vars`, never `encode`, so `encode.rs`'s own `Store` arm could not fire for an array-sorted store. Extensionality was therefore never instantiated and the array disequality stayed a free Boolean, so `(not (= (store (store a 1 x) 2 y) (store (store a 2 y) 1 x)))` — unsat QF_ALIA/QF_AUFLIA, and the shape the `storecomm_*` family is made of — answered `sat` in milliseconds. `oxiz-solver/tests/array_store_extensionality.rs` covers it with 10 tests, four of them sat controls.
  - **Exhausting the array-axiom budget was reported as "every axiom is satisfied."** On hitting `MAX_ARRAY_AXIOM_INSTANCES` (20,000 — unchanged) the routine did a bare `return false`, and `false` is its encoding of *the candidate model satisfies every axiom*, so the caller returned `Sat` outright. A new trail-scoped `array_axioms_incomplete` flag (`oxiz-solver/src/solver/array_axioms.rs:72`, `:135`) now nulls the model and answers `Unknown` at the gate in `mod.rs:813`, and `pop` restores it. Tests: `array_axioms.rs`'s `budget_honesty_tests` — `an_exhausted_instance_budget_is_unknown_not_sat`, `an_available_budget_still_decides_the_same_formula`.
  - **The verdict could depend on how loaded the machine was.** Integer case-split refinement is skipped when the first solve already blew a wall-clock ceiling, and the skip used to short-circuit the call away — but `split_narrow_int_domains` is also what *discovers* whether a candidate has unbranched shared-term domains. With a plain `affordable && split(..)`, in the source comment's own words, "the gate never heard about a candidate whose refinement the ceiling declined, so the verdict depended on machine speed — `sat` under load, `unsat` idle" (`oxiz-solver/src/solver/check_core.rs:364-380`). Skipped targets are now still counted (`case_split_skipped_targets`, `int_case_split.rs:294`) and mark the `Sat` unverified, which the gate at `mod.rs:823` turns into `Unknown`. The ceiling itself went **5 s → 120 s** (`REFINEMENT_TIME_CEILING_MS`, `int_case_split.rs:110`): it was chosen when the only refinement was the single-atom reading, whose targets are found in milliseconds, but the QF_UFLIA `Wisa` instances the new LP relaxation exists for take a *minute* to reach their first candidate model — at 5 s the refinement was built, correct, and forbidden from running. Tests: `an_unaffordable_round_marks_the_candidate_unverified`, `an_unaffordable_round_with_no_targets_changes_nothing`.
  - **Nothing could bound a term that no single atom bounds** — new module `oxiz-solver/src/solver/int_range_lp.rs` (395 lines). This is [#46](https://github.com/cool-japan/oxiz/issues/46)'s root cause: an integer UF argument whose finite range is implied only by a *difference of two individually free* variables is invisible both to `compute_int_bounds` (single-variable facts only, a deliberate guard against an earlier false-`unsat`) and to the simplex's per-variable propagation, so `refine_int_case_split` never emitted its `(or (= t lo) … (= t hi))` lemma and CDCL had no atom on which to branch the shared term's value. The new module asserts **every** arithmetic atom that is true at decision level 0 — the same facts the single-atom reading already trusts, with the single-term restriction lifted — into a throwaway rational LP with one column per distinct term, then minimises and maximises the target column and rounds inward (`ceil(min)`, `floor(max)`). A bound is taken only from a proved `Optimal`; `Unbounded`, `Unknown` and `Infeasible` all yield nothing, deliberately, because a pivot-budget `Unknown` incumbent is merely feasible and not optimal. Dropping integrality and treating distinct `TermId`s as independent columns can only *enlarge* the feasible set, so the interval over-approximates and a case-split built from it cannot exclude a reachable value. Bounded at 4,096 atoms, 4,096 columns and 48 LP queries per round, with 8 inline tests.
  - **Store chains reduced one level per refinement round** (`oxiz-solver/src/solver/array_axioms.rs:261`, `:291`). Read-over-write now walks up to `MAX_STORE_CHAIN_DEPTH = 128` levels of a `store` spine in a single round, where before an *n*-deep chain cost *n* full re-solves from root. Deeper chains still reduce — the remaining levels simply arrive over later rounds, exactly as they did before — so this is a latency fix, not a soundness fix.
- **The SAT engine could silently lose a level-0 implication after strengthening a clause** (`oxiz-sat/src/solver/learn.rs`). Re-attaching watches after removing a literal is not enough: a watch fires only on a *newly* falsified literal, so a clause that becomes unit under the assignment already on the trail has no future event to fire on — a "hanging unit" that costs an implication with no diagnostic in release builds. `remove_literal_and_rewatch` (`:838`), `vivify_clauses` (`:944`), `inprocess` (`:1091`) and `equiv.rs`'s `fold_equivalent_literals` (`:403`) now rewind the propagation head. `inprocess` had a second, sharper form of the same bug: it runs immediately after conflict handling, where the level-0 propagation queue is routinely non-empty, and the probe decision level opened by `strengthen_clauses_inprocessing`/`vivify_clauses` drained those pending literals *under the probe's assumptions*, filing the consequences at the probe level for the following `backtrack` to discard — the genuine level-0 implications were then never re-derived. Guarded by `issue36_bve_and_subsumption.rs::test_issue36_inprocessing_leaves_no_hanging_unit` (200 randomized rounds; it reproduces only with a short inprocessing interval, which is why the default of 5000 hid it). In the same file, `remove_literal_and_rewatch` now clamps a strengthened clause's LBD to its new length (`:812`) — LBD counts distinct decision levels and cannot exceed clause length, and a ternary that became binary while keeping LBD 3 tripped the debug invariant outright.
- **Substitution could fabricate a 32-bit-wide `concat`.** `TermManager`'s substitution rebuild and `oxiz-core`'s e-matching apply path both called the infallible `mk_bv_concat`, whose release-build fallback invented a width; the result is an ill-sorted term that can flip an answer between `sat` and `unsat`. Both now call `try_mk_bv_concat(a, b).unwrap_or(id)` (`oxiz-core/src/ast/manager/query/substitute.rs:812`, `oxiz-core/src/ematching/substitution/apply.rs`), declining to apply an ill-typed map and keeping the original term — a weaker result, but a sound one. A sort-preserving substitution can never reach that branch; it exists only so the unreachable case fails safe.
- **`RecFunSolver::pop` retracted an arbitrary subset of the wrong scope** (`oxiz-theories/src/recfun.rs`). It read `seen_apps.iter().skip(size)` over a `HashSet`, whose iteration order is unspecified — so `skip(n)` named an arbitrary *n*-element prefix: applications belonging to enclosing scopes were retracted (then looked unseen and were re-registered and re-counted) while applications the popped scope actually owned survived their own retraction, and re-entering the scope silently skipped them. Fixed with an insertion-ordered `app_trail: Vec<FunApp>` and trail-length snapshots in `context_stack`. New tests `pop_retracts_exactly_the_applications_of_the_popped_scope` (32 applications, chosen so hash order diverges from insertion order — it fails against the old code) and `repeated_registration_does_not_double_count_the_trail`.

### Added

- **`rhai` is now optional, behind a `scripting` Cargo feature that is ON by default — and with it goes the only non-permissively-licensed crate OxiZ has ever pulled in.** Before this, `oxiz-core`'s `std` feature listed `rhai` unconditionally, so the embedded scripting engine was in every build that could solve anything at all, including one that only encodes goals and calls `check-sat`. It exists for exactly one type — `oxiz_core::tactic::ScriptableTactic`, which runs a user-supplied Rhai script as a tactic — and nothing in the workspace constructs one, because the script string has to come from the consumer. The cost of carrying it is not mainly code size: **`rhai` depends on `smartstring`, which is `MPL-2.0+`, and MPL-2.0 is copyleft.** A downstream whose `cargo deny check licenses` allows only Apache-2.0 / MIT / BSD / ISC / Zlib / CC0 / Unicode — the COOLJAPAN house policy, and the one AstRS enforces in CI — could not depend on `oxiz` at all, at any feature setting, and the failure named a crate three levels below anything it had asked for. There is now a knob, and it costs a default build nothing: `scripting` joins the default feature set of both `oxiz-core` and the `oxiz` meta crate (and `oxiz`'s `standard`, hence `full`), so **a consumer that says nothing gets the API and the behaviour it had in 0.3.2.**
  - **The exact selection for a consumer that wants a permissive-only licence graph** is `oxiz = { version = "0.3.3", default-features = false, features = ["std"] }`. `scripting` implies `std`, never the reverse. That build was verified end to end against AstRS's own `deny.toml`: `cargo deny check licenses` **passes** on the reduced graph and **fails on the default one**, rejecting `smartstring v1.0.1`'s `MPL-2.0+`; `cargo tree -p oxiz --no-default-features --features std -e normal | grep -Ei 'rhai|smartstring'` is empty, while the default tree still shows both. `cargo deny check bans` is clean in both. Note that dropping the defaults also drops `nlsat` (see the entry below); a consumer that wants nonlinear arithmetic *and* a permissive graph asks for `features = ["std", "nlsat"]`.
  - **Nothing degrades silently, because there is nothing to degrade.** With the feature off, `ScriptableTactic` does not exist — a missing type, caught at compile time, not a stub that accepts a script and quietly ignores it. Every other tactic, probe, combinator and re-export in `oxiz-core::tactic` is untouched, and no solving path changes: the type is never reachable from `check-sat`. This is the one case where a feature gate needs no honesty gate, and the test counts say so — `oxiz-core` runs 2,179 tests with the feature and 2,171 without, the difference being exactly the eight `ScriptableTactic` tests, which are `cfg`'d individually rather than moved.
  - **`rhai` is named `dep:rhai`, so there is no implicit `rhai` feature.** That is deliberate and is the one thing here a consumer could notice: `oxiz-core = { features = ["rhai"] }` was accepted in 0.3.2 and is now an error. Keeping it working would have been a trap rather than a courtesy — with the code gated on `scripting`, it would pull the MPL-2.0 dependency into the licence graph and hand back **no API at all**, which is the precise combination this feature exists to make unreachable. The other change a `default-features = false, features = ["std"]` user of `oxiz-core` will see is that `std` alone no longer carries `ScriptableTactic`; add `"scripting"` to get it back. In-workspace consumers needed no such edit: none of them constructs one.

- **`oxiz-nlsat` is now optional, behind a `nlsat` Cargo feature that is ON by default.** Before this, `oxiz-theories`'s `std` feature listed `oxiz-nlsat` unconditionally, so the cell-decomposition nonlinear-arithmetic core was in every build that could solve anything at all — including `wasm32` builds of a purely propositional demo that never issues a nonlinear goal. `twiggy` attributes 70,571 raw bytes (4.9 % of the module) to the crate itself in the COOLJAPAN Playground's `/oxiz` shim, which is the first consumer to run out of size budget; **the measured saving is larger than that, because dropping the crate also drops everything only it reached.** On a browser shim built with `opt-level = "z"`, fat LTO, `codegen-units = 1`, `panic = "abort"`, stripped, and `wasm-opt -Oz --converge`: **1,557,287 → 1,363,027 bytes raw (−194,260, −12.5 %) and 573,181 → 504,913 after `gzip -9` (−68,268, −11.9 %)**. There is now a knob, and it costs a default build nothing: `nlsat` joins the default feature set of `oxiz-theories`, `oxiz-solver` and the `oxiz` meta crate, so **a consumer that says nothing gets the behaviour it had in 0.3.2**. Every in-workspace consumer that named `features = ["std"]` explicitly (`oxiz-cli`, `oxiz-opt`, `oxiz-spacer`, `oxiz-smtcomp`, `oxiz-ml`, `bench/regression`, `bench/profile`) now names `["std", "nlsat"]` for the same reason — the workspace dependency table sets `default-features = false`, so for those crates the feature list is the whole feature set and inheriting the new default was not an option.
  - **`oxiz-wasm` forwards it as a feature of its own** rather than hard-wiring it, because a browser bundle is precisely the consumer that may want it gone: `nlsat` is now listed in that crate's `full` feature (and therefore in its `default`), so nothing about an existing build changes, while `--no-default-features --features minimal` drops `oxiz-nlsat` from the graph. **This is the first thing `minimal` has ever actually removed.** `proof`, `interpolation`, `spacer`, `ml_branching` and `wasm_bench` are empty feature lists that pull in no dependency and gate no code — the only `cfg!(feature = …)` sites in the crate are `FeatureRegistry`'s own reporting accessors — so the "~35–45 % size reduction" the manifest advertised and the per-subsystem estimates in `src/feature_registry.rs` (~180 KB proof, ~90 KB interpolation, ~220 KB Spacer, ~130 KB ML, ~25 KB bench) were never true: selecting `minimal` over `full` could not remove anything, because there was nothing gated to remove. That is checkable in one command — `grep -rn 'cfg(feature\|cfg!(feature' oxiz-wasm/src/` returns those accessors and nothing else. Those numbers are replaced with the measured figures above and an explicit note of which rows gate nothing. `FeatureRegistry` gains `has_nlsat()` and reports it in `enabled_features()` / `disabled_features()` / `is_minimal()` like its neighbours.
  - **The exact selection for a consumer that wants everything except nonlinear arithmetic** is `default-features = false, features = ["std"]` on `oxiz-solver` (and on `oxiz-theories` / `oxiz` if named directly). `nlsat` implies `std`, never the reverse. Note that dropping the defaults also drops `oxiz-solver`'s `property-tests`; a *test* build of that combination wants `features = ["std", "property-tests"]`.
  - **What OFF costs is completeness, and only on QF_NRA.** Three procedures that were never in `oxiz-nlsat` stay compiled in: the static UNSAT pattern detector (`check_core`'s `check_nonlinear_constraints`) and the two model searches (`oxiz-theories`'s `nl_repair_search` and `nl_ground_reduce`), whose every `sat` is re-verified against the untouched assertions in exact `BigRational` arithmetic by `nl_eval::holds_under` before it is reported. `oxiz-solver` gates those searches on QF_NIA, so **QF_NIA answers identically with the feature on or off** (measured: `x*x = 4` → `sat`, `x*y = 6 ∧ x+y = 5` → `sat`, `x*x = 3` → `unsat`, `x*x = -1` → `unsat` in both), while **QF_NRA loses every nonlinear verdict to `unknown`** — including ones it could have refuted, such as `x*x < 0`. QF_NRA's *linear* fragment is unaffected.
  - **The concession is the existing honest-`Unknown` path, not a new one.** With the dispatch compiled out, a nonlinear atom is exactly what `check_core`'s `arith_atoms_need_theory` gate already exists to catch — an arithmetic atom the linear solver could not represent, which `encode.rs` left as a free Boolean — so it answers `Unknown` rather than letting the SAT layer pick a truth value for it, the same way it already declines String and FP atoms no theory can take. No new error type, no panic, and no `unwrap`: a later `(get-value …)` renders an in-band `(error "No model available")` line, which matters because the `wasm32` consumer this was cut for builds with `panic = "abort"` and cannot catch a trap.
  - **Tests**: `oxiz-solver/tests/nlsat_feature_gate.rs` is new and runs in both combinations. Its Boolean / QF_LIA / QF_UF-unsat-core / linear-QF_NRA / QF_NIA groups carry no `cfg` at all — they must produce the same answers in both builds, which is what makes them a no-regression proof rather than two expectations — and the QF_NRA group is `cfg`-split so each build states its own. `oxiz-theories`' three nlsat-dependent test files (`nlsat_mixed_sort.rs`, `pr27_nia_divmod.rs`, and the `nlsat` section of `c4_theories_deep_recursion.rs`) are gated on the feature so `cargo test -p oxiz-theories --no-default-features --features std` compiles and passes. Five existing `oxiz-solver` tests are marked `#[cfg(feature = "nlsat")]` individually, each with its reason: three QF_NRA verdicts in `nlsat_integration.rs`, `model_output_and_options.rs`'s `test_reset_assertions_keeps_logic_selected_theory` (whose subject *is* the NLSAT installation surviving `(reset-assertions)`), and `nlsat_integration.rs`'s `test_nia_push_pop_backtrack` — the last of these for an ordering reason worth knowing: its contradictory level is purely linear, but `check_core` consults the honesty gate *before* the CDCL(T) search, and only `dispatch_nl_solver` runs ahead of that gate. Its OFF-build counterpart, asserting the same sequence concedes rather than reporting a spurious `Sat`, is in the new file.
  - **Not a soundness change and not an API break.** `oxiz`'s `nlsat` feature previously controlled only the `oxiz::nlsat` re-export while the crate itself was compiled regardless; it now also forwards to `oxiz-theories/nlsat` and `oxiz-solver/nlsat`, and joins `default`. The only difference visible to an existing `oxiz = "0.3"` user is that the re-export they could already opt into is now present out of the box.

- **Recursive functions (`define-fun-rec` / `define-funs-rec`) are supported end to end.** Since 0.3.1 they were an honest hard parse rejection ("recursive function definitions are not supported"), which was itself a fix for the version before that, where the command was balance-skipped and its symbol left as an unconstrained uninterpreted function — every `(f x)` survived and every constraint on `f` vanished, so `unsat` came back as `sat` with a meaningless model. They are now parsed (`oxiz-core/src/smtlib/parser/recfun.rs`, new), carried as `Command::DefineFunsRec` and discharged by fuel-bounded unfolding of `∀x. f(x) = body` (`oxiz-solver/src/context/recfun.rs` + `recfun/eval.rs`, new). **Mutual recursion works**, via a strict two-pass parse that registers every signature in the group before any body is read, so `is-even`/`is-odd` resolve through the ordinary declared-symbol path and build real `Apply` nodes; nothing is ever put into the parser's `bindings` or `function_defs`, the two inlining paths, because an inlined recursive body would not terminate.
  - **Instantiated equations are consequences, so `sat` needs a certificate and `unsat` does not.** The instantiated problem is a *relaxation* of the original, so `unsat` is returned immediately and is final. `sat` is published only with one of two certificates: **saturation** — the round was not truncated and the unfolding boundary is empty, i.e. every reachable application got its instance — or **model re-computation** (`recfun/eval.rs`), where a ground evaluator recomputes every recursive application in the user's own assertions straight from the definitions and confirms the model already agrees. Anything else is `unknown`, in finite time. A refuted certificate feeds the concrete applications it pinned back in as the next round's seeds, which is what lets a query with a *symbolic* argument converge.
  - **All budgets are compile-time constants, not config** (`oxiz-solver/src/context/recfun.rs`): `FUEL_SCHEDULE = [4, 8, 16, 32]` instances per round — escalated only when a round taught the driver nothing new, never on a timer — `MAX_ROUNDS = 16` solver calls per `check-sat`, `MAX_LEARNED_APPS = 256`, `MAX_INSTANCES = 100_000` per round (hitting it marks the round truncated, which *disables* the saturation certificate: a worklist drained by truncation is not a worklist that closed), `EVAL_BUDGET = 200_000` steps and `MAX_EVAL_APPS = 2_000` distinct applications in the certifier. Fuel exhaustion is always an honest `unknown` — `f(x) = f(x+1)` answers `unknown` rather than hanging, while the inconsistent `f(x) = f(x) + 1` is still correctly `unsat` because its very first instance is contradictory. Instances are asserted in a scratch scope on `Solver::assert`, never `Context::assert`, so `(get-assertions)` is byte-identical to before.
  - **Documented gap:** saturation covers only *reachable* arguments, so `f(n) = ite(n = 0, 0, f(n) + 1)` with only `(= (f 0) 0)` asserted is reported `sat` (z3 4.15.4 answers `sat` here too). **Tests:** 21 in `oxiz-solver/tests/recfun_e2e.rs` (`fact_5_is_120`, `mutual_parity_even_four`, `mutual_parity_cannot_be_both`, `symbolic_argument_solves_for_the_variable`, `nonlinear_symbolic_argument_is_honestly_unknown`, `non_terminating_definition_answers_unknown_without_hanging`, `inconsistent_definition_is_unsat`, `definition_goes_out_of_scope_on_pop`, `check_sat_assuming_respects_the_definition`, `get_consequences_respects_the_definition`, …), 5 parser tests in `oxiz-core/tests/audit_parser_cmds.rs`, 3 inline.

- **`RoundingMode` is a first-class sort.** Until 0.3.0 `(declare-const m RoundingMode)` fell through to the generic uninterpreted-sort fallback and silently built a fresh *free* sort — a domain with unboundedly many elements where SMT-LIB specifies exactly five. 0.3.0 replaced that with an honest parse rejection; 0.3.3 implements it. `SortKind::RoundingMode` is a real sort (`oxiz-core/src/sort/mod.rs:84`) eagerly interned by `SortManager::new` at `SortId(3)`, and the five modes are ordinary nullary `Var` terms interned at it (`oxiz-core/src/ast/manager/rounding_mode.rs`, new) — no new `TermKind`, which is exactly why EUF already decides equalities between them with no theory-dispatch change. Short and long spellings (`RNE` / `roundNearestTiesToEven`, …) hash-cons to the identical `TermId`.
  - **Cardinality is enforced by two axioms** (`oxiz-solver/src/context/rounding_mode.rs`, new), both asserted through `Solver::assert` so they stay out of `(get-assertions)` and both guarded on `TermManager::rounding_mode_used()` so a script with no rounding mode pays nothing: a **closure** axiom `(or (= m RNE) … (= m RTZ))` per declared constant, and one **distinctness** axiom `(distinct RNE RNA RTP RTN RTZ)` per solve. The pairing is what makes both directions right, and the test file states the check crisply: drop distinctness and `(distinct m0 … m4)` flips to `unsat`; drop closure and `(distinct m0 … m5)` flips to `sat`.
  - **A symbolic mode inside an `fp.*` operator expands to a five-way `ite`** over the concrete-mode instances (`oxiz-core/src/smtlib/parser/build.rs:452`), with the final `RTZ` branch left unguarded — sound only because of the closure axiom and the new **binder relativization** (`parser/terms.rs:844`), which rewrites `forall` over a `RoundingMode` variable to `(=> (and closure(v) …) body)` and `exists` to `(and closure(v) … body)`. Without it a `forall` was strictly *stronger* than SMT-LIB's (a formula true of every real mode could come back `unsat`) and an `exists` strictly *weaker* (witnessable by a sixth non-mode value). The same dispatch covers the indexed conversions `to_fp`, `to_fp_unsigned`, `fp.to_sbv`, `fp.to_ubv`.
  - **Model extraction reads the mode out of the closure axiom's own equality atoms** (`oxiz-solver/src/solver/model_builder.rs:273`), rather than falling through to `Context::default_value`, which always answers `roundNearestTiesToEven` — so `(assert (not (= m RNE)))` used to answer `sat` and then print a model falsifying its own assertion. The equality-skeleton fast path now also *excludes* `RoundingMode`-sorted constants (`oxiz-solver/src/solver/eq_skeleton.rs`): they are nullary `Var`s that look exactly like uninterpreted constants, but a pure-equality graph reasons only about the equalities written in the formula and would happily satisfy six pairwise-distinct rounding modes. `z3_compat` reports the sort as `Z3SortKind::Other` rather than folding it into `Uninterpreted`, for the same reason.
  - **Restriction, stated honestly rather than silently widened:** `RoundingMode` is accepted only in *nullary* declaration position (`declare-const` / `declare-fun` with no arguments). As an array domain or range, a function argument sort, the result sort of a function with arguments, or a datatype field sort it is a parse error naming the position, because there is no way to attach the closure axiom to the modes reachable through it, and accepting it would silently treat the sort as infinite again. **Tests:** 14 in `oxiz-solver/tests/rounding_mode_first_class.rs`, plus two new parity benchmarks — `bench/z3_parity/benchmarks/qf_fp/fp_symbolic_rm_sat.smt2` (a symbolic mode inside `fp.add`, on operands whose sum is exactly representable so every mode agrees) and `fp_symbolic_rm_unsat.smt2` (six pairwise-distinct `RoundingMode` constants; a solver that models the sort as ordinary uninterpreted answers `sat` here).

- **A nonlinear-integer relaxation engine, on by default** (`oxiz-theories/src/arithmetic/nla/`, new — `SolverConfig::nonlinear_relaxation_engine`, `true` everywhere except `minimal`). Where the existing QF_NIA path was cell-decomposition plus two sat-only searches that are structurally unable to report `unsat`, this is NIA-over-LP in the spirit of Z3's `math/lp/nla_*`: every product of two or more non-constant factors is replaced by a fresh variable with a recorded *monic* side-constraint (`linearize.rs`), and the engine then loops LP feasibility, an exact `BigInt` monic-consistency check, interval propagation to fixpoint (`monomial_bounds.rs`), McCormick and square-tangent cuts, and finally an integer case split (`engine/branch.rs`) — sign splits `x ≤ −1 ∨ x = 0 ∨ x ≥ 1` and value splits `v ≤ k ∨ v ≥ k+1`, both tautologies over `ℤ` and only over `ℤ`. It is dispatched *after* the cell-decomposition core, so no verdict that core reaches can move; what it converts is goals that previously answered `unknown`. `x ≥ 3 ∧ y ≥ 3 ∧ x·y ≤ 8`, `x² + y² + 1 = 0`, `y = x − 5 ∧ y·y < 0` and `x,y,z ≥ 2 ∧ x·y·z ≤ 7` are now `unsat`; each is pinned as a *paired* measurement in `oxiz-solver/tests/qf_nia_relaxation.rs` (flag on ⇒ `unsat`, flag off ⇒ `Unknown`), which is what makes the test evidence of the wiring rather than of the pre-existing static pattern detector.
  - **Both verdicts are backed, not guessed.** `unsat` comes only from an LP infeasibility closure over constraints that are all consequences over `ℤ` of the input, with case splits exhaustive over `ℤ`; the linearisation may *drop* a conjunct it cannot translate (`div`/`mod`), which only weakens the problem, and an unsatisfiable weakening still refutes the original — while a dropped conjunct suppresses `sat` to `unknown`. `sat` is advisory by the module's own contract and is re-verified twice: once inside the module against the untouched assertions in exact `BigInt`/`BigRational`, and again by `Solver::adopt_nl_witness`. A witness that fails yields no verdict at all and falls through to the model searches. Gated on `std` rather than on `nlsat`, so it is present in both builds; 86 tests.
  - **Deliberately not done, and recorded as such** (`nla/mod.rs`): no Gröbner/S-polynomial layer, no Horner form (so `x·y − x·z` is bounded as though the two `x`s were independent), no handoff back to the cell-decomposition core, and backward root propagation only for single-power monics. Three of the ten lemma constructors are carried but `#[allow(dead_code)]` — `order` and `monotonicity`, because the pairing pass that could discharge their premises does not exist yet, and the bilinear `tangent`, which McCormick supersedes over a finite box — said in the source rather than implied by the family list.
  - **One visible consequence:** the engine sits above the two `nonlinear_model_search` procedures, so a goal both can solve is now answered by the engine and reports *its* witness. Both are re-verified and both are correct, but on a multi-solution goal they need not be the same one — `x·y = 6 ∧ x + y = 5` reports `(2, 3)` in the default build and `(3, 2)` without `nlsat`. A caller pinning an exact `(get-value …)` string for a multi-solution QF_NIA goal may see it change; the tests assert valid-solution *sets* for exactly this reason.

- **Algebraic-number witnesses: an irrational root is now a model, not an `unknown`.** `(assert (= (* x x) 2.0))` in QF_NRA answers `sat` and prints `(root-obj (+ (^ x 2) (- 2)) 1)` — the `root-obj` rendering (`oxiz-solver/src/context/model_fmt.rs:23-104`) reproduces z3 4.15.4's spelling rule for rule, each row of the table captured from the real binary: descending degree, zero coefficients omitted, `(^ x k)` for k ≥ 2 and a bare `x` for k = 1, unit coefficients elided, `(- n)` for negatives, and the bound variable always printed `x` whatever the SMT constant is called. The value carrier is a new dedicated type (`oxiz-theories/src/nl_witness.rs`) holding integer coefficients, a root index and an isolating interval, and it travels on its own channel: `NlDispatchResult::Sat` now carries either a rational `Interpretation` or an algebraic map, never both, and the channel is cleared on entry to every dispatch and invalidated by `pop` and by any later `assert`.
  - **The `get-value` line is byte-identical to z3; `(get-model)` is not** — OxiZ wraps in `(model …)` with one `define-fun` per line where z3 emits a bare parenthesised block. Only the value string is pinned, and `oxiz-solver/tests/nra_algebraic_model.rs` says so in its own header.
  - **Two honest gaps, both documented and both tested.** The polynomial carried is the defining polynomial, **not** the minimal one: `x⁴ = 4` renders the unfactored `x⁴ − 4` where z3 factors and prints the degree-2 form. Both denote √2; the spellings differ. And `(get-value ((* x x)))` over an algebraic constant *echoes the term* rather than answering `2.0` as z3 does — OxiZ cannot yet compute in the algebraic field. The property `a_compound_query_over_an_algebraic_constant_does_not_fabricate_a_value` pins only that it does not invent `0.0`.
  - **The refusal boundary is one algebraic value at a time, not one algebraic variable.** A goal with three variables of which one is algebraic is answered (`a_mixed_algebraic_rational_and_unconstrained_model_matches_z3`); a *second* algebraic value in the same assignment leaves a genuinely multivariate real-algebraic problem the crate cannot solve, and it returns `unknown` rather than guess — `x² = 2 ∧ y² = 3` answers `unknown`. A root atom anywhere in the instance is likewise refused wholesale, and a final sweep requires every Boolean-assigned atom to be *proved* to agree with its polarity before `sat` is published. 9 tests.
  - **Five root-isolation correctness fixes came out of the same work** (`oxiz-nlsat/src/`): bracket overlap now requires *strict* separation, because touching brackets let `open_sample` land exactly **on** a root and leave an open cell with no representative, so a caller enumerating one point per cell would conclude the set empty; exact-rational root search moved to a half-open `(lo, hi]` bracket, because admitting a root at the lower endpoint replaced `−√2` with a duplicate of `0` for `x³ − 2x` and dedup then discarded it, leaving 2 of 3 real roots; new proof-only `try_sign_of` / `try_sign_at_algebraic` return `None` on refinement-budget exhaustion instead of falling back to the midpoint *guess* the old `sign_of` used, and every decision a wrong answer would ride on now goes through them; atom evaluation routes through `Assignment::eval_poly_sign`, which is where `x = √2` followed by `y = 1` into `x·y = 1` surfaces as a contradiction rather than `Undef`; and `is_integer_solution` now answers `false` for an algebraic point — without which QF_NIA `x·x = 2` would have answered **`sat`**. It answers `unsat`.

- **Gomory mixed-integer cuts are reachable for the first time.** The generators in `oxiz-theories/src/arithmetic/lia/cuts.rs` were real — GMI and pure-integer Gomory fractional cuts derived from the actual simplex tableau row, returning `None` rather than fabricating one — but `LiaSolver::generate_conflict_driven_cut` had **zero callers anywhere in the repo** and `LiaConfig::enable_gomory_cuts` was declared, defaulted, and never read. A new root cutting-plane loop (`lia/branching.rs`) runs up to `ROOT_CUT_ROUND_LIMIT = 8` rounds as step 0 of `LiaSolver::check`, *before* any branch-and-bound `push`, so the cuts' slack rows are scoped by the caller and can never be popped away with a branch; a simplex `Err` on adding one is an integer-infeasibility proof. Branch-and-bound itself stays cut-free deliberately — a branch-local cut derives from a tableau that already includes the branch bound and would need retraction wiring, which is recorded as follow-up rather than half-built. `enable_gomory_cuts` is `true` in `LiaConfig::default()` and `TheoryConfig::fast()`, `false` only in `TheoryConfig::small()`. A new `LiaSolver::check_balanced` pops every branch scope on every exit path (winning, infeasible, and both resource-limit paths) after snapshotting the model at the satisfying leaf, where plain `check` deliberately *retains* the winning branch's `push` so the model stays queryable — poisonous for a caller that keeps asserting afterwards, since every later assertion would land inside a branch scope and be silently retracted by the next `pop`. That, plus the new scope/bound delegation in `lia/scope.rs`, is what the NLA engine above is built on. 8 new tests; no timing numbers are claimed.

- **A pre-search "lucky" phase in the SAT engine** ([#35](https://github.com/cool-japan/oxiz/issues/35); `oxiz-sat/src/solver/lucky.rs`, new; `SolverConfig::enable_lucky_phase`, `true` by default and in all ten presets). Six scans are tried in order before the search starts — all-true, all-false, forward-ordered and backward-ordered greedy single passes, the Horn least model and the dual-Horn greatest model — each built in scratch buffers over a frozen base of level-0 trail values plus resolved assumptions, and each verified against the live *original* clauses (learned excluded) before it is installed. It declines outright if an assumption contradicts a level-0 fact, so the ordinary UNSAT-core path is unaffected. Two call sites, `Solver::solve` and `Solver::solve_with_assumptions`, both after the initial level-0 propagation; it is deliberately **not** wired into `solve_with_theory`, because a `TheoryCallback` learns the trail through `on_assignment` and a scratch-buffer assignment never calls it — so the ordinary SMT `check()` path never runs it, only `check_sat_only` and the equality skeleton do. New `lucky_attempts` / `lucky_successes` statistics exist specifically so "the phase is neutral here" can be told apart from "the phase never ran". **No speedup figure is claimed**: the example `oxiz-sat/examples/lucky_phase_benchmark.rs` computes its numbers at runtime and records none, and the only figures in the tree are the reporter's own. 14 integration tests including a 400-instance differential sweep requiring identical verdicts with the phase on and off, plus 12 unit tests.

- **Bounded variable elimination is reachable, and self-subsuming resolution exists** ([#36](https://github.com/cool-japan/oxiz/issues/36)). BVE was fully implemented and completely unreachable: `enable_bve` was `false` in `oxiz_sat::SolverConfig::default()` and in all ten presets, and `oxiz-solver` had no way to set it at all. `oxiz_solver::SolverConfig::enable_bve` is new and maps onto the SAT flag (`true` in `thorough`, `false` elsewhere); `oxiz_sat`'s `Industrial` and `CaDiCaL` presets now enable it. Both are safe against the documented rough edges because the pass already refused to run under an incremental `push`, under proof tracing, at a non-zero decision level, or alongside equivalent-literal substitution — and BVE runs only from `Solver::solve`, never from `solve_with_theory`, so no theory lemma can be blocked by an eliminated variable on the normal SMT route. The one reachable rough edge is named in the field doc: a caller that mixes `check_sat_only` with later incremental assertions can hit `SolverError::EliminatedVariableReintroduction`, which turns later verdicts into `Unknown` until `reset()` rather than risking a wrong answer — which is why `balanced`, the default, leaves it off.
  - **Self-subsuming resolution was absent crate-wide**, and the reason it stayed unnoticed is instructive: `Clause::self_subsuming_resolvent` existed but its length guard was `self.lits.len() >= other.lits.len()`, which rejects *equal-length* pairs — the single most common shape (`(a∨b∨c)` against `(a∨b∨¬c)` → `(a∨b)`) — so the rule fired on almost nothing, and it had no production caller to notice. The guard is now `>` and a real occurrence-driven pass lives in `oxiz-sat/src/solver/self_subsumption.rs` (new; collect-then-apply with re-verification against the live database before each application, caps of 20 literals per clause / 256 strengthenings per pass / 64 candidates per literal, skipping level-0 trail antecedents, refusing to run under LRAT, and registering both binary-implication-graph edges itself when a strengthening lands on exactly two literals). `enable_self_subsumption` defaults to `true` — but it runs from `Solver::inprocess`, so it is **inert wherever `enable_inprocessing` is false**, which includes `oxiz_sat::SolverConfig::default()` and five of the ten presets. It is live in `Industrial`, `Cryptographic`, `Hardware`, `Conservative`, `CaDiCaL`, and through `oxiz-solver`'s `balanced` and `thorough`.
  - **The subsumption pass itself had three defects and a panic**, all in `oxiz-sat/src/preprocessing_core.rs:334` and all found only once BVE was actually reachable. It was order-sensitive — the loop only ever tested *earlier subsumes later*, so adding `(x0 ∨ x1)` before `(x0)` left both alive while the same two clauses in the other order retired one; its occurrence index was computed and then **never read**, so it rescanned every later clause for every clause; fixing the order-sensitivity introduced a duplicate hazard (two identical clauses subsume each other, and a naive both-directions fix deletes both), now broken by clause id; and `OccurrenceList`'s `add`/`get`/`remove` indexed straight into a table sized from `num_vars`, so a clause mentioning a higher-numbered variable panicked. 8 + 5 integration tests and 10 unit tests, including a 200-round randomized diff of the occurrence-accelerated pass against a naive all-pairs reference with a non-vacuity assertion.

- **A refuted candidate model is excluded and retried instead of conceding** ([#40](https://github.com/cool-japan/oxiz/issues/40); `oxiz-solver/src/solver/model_blocking.rs`, new; `SolverConfig::enable_model_blocking` / `max_model_blocking_rounds`, on with a 64-round per-scope budget everywhere except `minimal`). Two things landed. First an ordering fix that applies regardless of the flag: the `model_refutes_assertions` gate used to sit *above* the two working repair paths — non-convex LIA case-splitting and array-lemma refinement — so a repairable candidate was thrown away before either could see it; the gate now runs below both. Then the blocking loop itself. The blocking clause is deliberately **not** treated as a lemma, because the gate fires on two different triggers: a genuinely falsified assertion (entailed) and `EvalOutcome::Unrepresentable`, which is a statement about the fixed-width evaluator overflowing, not about the assignment. So it is a *search restriction*: `Sat` afterwards is still genuine and re-checked by the same gate, and while any blocking clause is live an `Unsat` from the SAT core means "no model outside the excluded region", which is not `unsat` — all three sites that could surface one (`check_core`, the equality-skeleton fast path, and `check_sat_only`) now demote it to `Unknown` and null the model and core. The lattice is `Unknown → {Sat, Unknown}`; turning the flag off buys a fast `unknown` at the price of the models it would have found, and does **not** restore the pre-#40 solver exactly, because with the gate below the array-axiom loop that loop's budget exit now also drops the candidate it was holding. 6 integration tests and 10 unit tests; the trigger formula uses 2⁶² so `(+ x x)` overflows `Rational64` on purpose.

- **`oxiz-core`'s own lightweight theory layer does something.** `oxiz_core::theories::combination::Theory` was a trait with **zero implementors** outside a test mock, and `TheoryCombiner` had no way to hold a theory at all; the five theory modules recorded axioms as data and their `propagate` methods were literally `{ self.propagations += 1; Vec::new() }` with a "placeholder" comment. All five (`ArrayTheory`, `BitVectorTheory`, `DatatypeTheory`, `FloatingPointTheory`, `StringTheory`) now implement `Theory`, each backed by a shared union-find with an explanation edge graph (`theories/eq_classes.rs`, new — explicitly *not* congruence closure), with real fixpoint propagation and conflict detection that returns an explanation chain; `TheoryCombiner::run` is a genuine fixpoint loop that routes deduced equalities through Nelson-Oppen and stops on no-change or first conflict. The new algorithms are constant folding and operator congruence for bitvectors, and acyclicity/occurs-check, injectivity, selector and tester application for datatypes — **no new operations were added**: `BitVectorOp`, `BitVectorAxiom` and `DatatypeAxiom` gained zero variants. A new `# Scope` section on the module says what this layer is and is not: "deliberately incomplete, and none of these theories is a decision procedure: 'no conflict found' never means 'satisfiable'" — the theories `oxiz-solver` actually runs still live in `oxiz-theories`, and nothing in this entry is wired into a solve path. 7 tests in `oxiz-core/tests/theories_nelson_oppen.rs` plus the modules' own suites.

### Fixed

- **OxiZ now runs on `wasm32-unknown-unknown`; before this it aborted on the first real `check-sat`.** That target has no clock, so `std::time::Instant::now()` is a hard `unreachable` in the standard library (`panicked at library/std/src/sys/time/unsupported.rs:13:9: time not implemented on this platform`). OxiZ read it *unconditionally* on the main solve path — the search-start stamp at `oxiz-solver/src/solver/check_core.rs:247`, which gates non-convex-LIA case-split refinement, is taken on every check and is **not** guarded by `timeout_ms > 0` — so under the wasm release profile's `panic = "abort"` every `(check-sat)` with at least one assertion trapped as `RuntimeError: unreachable`. Worse, an abort is not an unwind: the `Context`/`Solver` object stayed borrowed and every later call on it failed with *"recursive use of an object detected which would lead to unsafe aliasing in rust"*, so a browser session was permanently poisoned by its first solve. Parsing, `declare-*` and `assert` were fine, and `(check-sat)` on an empty assertion set short-circuited before the timer, which is why the failure only showed up on real work. `oxiz-wasm`'s own bindings were affected exactly the same way and could not solve anything as shipped, even though that crate's *own* code already routes its timestamps through `web_sys::Performance::now()` on wasm32.
  - New workspace crate **`oxiz-time`**: dependency-free, `no_std`, and the single place any OxiZ crate reads a clock. On every target that has one — which is every target except `wasm32-unknown-unknown`; `wasm32-wasip1` and emscripten keep their real clocks — `oxiz_time::{Instant, SystemTime, SystemTimeError, UNIX_EPOCH}` are **re-exports of the `std::time` originals**, so native timing behaviour, precision and public API are bit-identical to before (the crate carries a `const` type-identity proof of that, and every consumer carries a `const _: () = assert!(!oxiz_time::IS_FROZEN)` guard so a missing `oxiz-time/std` feature forward can never silently hand a native build the stub). On `wasm32-unknown-unknown` (and in `no_std` builds) they are frozen stand-ins: `Instant::now()` reads t = 0, `elapsed()` is `Duration::ZERO`, `SystemTime::now()` is `UNIX_EPOCH`. Nothing traps.
  - All 101 `std::time` references in the library crates were rewritten onto it — 47 files in the wasm dependency graph: `oxiz-core` (14 sites / 14 files), `oxiz-math` (4/3), `oxiz-sat` (10/7), `oxiz-nlsat` (3/3), `oxiz-theories` (12/10), `oxiz-solver` (17/8), `oxiz-proof` (5/2) — plus `oxiz-opt` (16/4), `oxiz-spacer` (7/6) and `oxiz-ml` (13/9), which are not wasm-reachable today but are the same landmine if they ever are. `oxiz-cli`, `oxiz-smtcomp` and the `bench/*` harnesses deliberately keep `std::time`: they are host-only binaries that cannot be built for wasm at all. Every rewritten site was reviewed for what the clock was doing there — a deadline that is `None` unless a timeout was set, a statistics accumulation, or a heuristic valve on a loop that also has a structural bound (iteration cap, finite worklist). No loop in the workspace had time as its only exit, so freezing the clock cannot turn a terminating search into a hang.

Bound a wasm search with `:max-conflicts` (note that the conflict budget is enforced in the theory callbacks, so it does not fire on purely propositional instances) and/or by terminating the Web Worker; measure wall time from JavaScript around the call. This is documented on `oxiz-time`'s crate docs and is the same trade-off the crate's `no_std` branches already made.
- **`oxiz-core` builds on `no_std` again.** `cargo check -p oxiz-core --no-default-features` had been failing with `error[E0433]: cannot find module or crate `std`` since before this release: `traits/propagator.rs`'s `PropagatorManager::propagate_all` sorted its queue with `std::cmp::Reverse`, in a module that is compiled on every configuration. `Reverse` is in `core::cmp` on all of them, so the fix is the one-token `::core::cmp::Reverse` — fully qualified because `crate::tactic::core` makes a bare `core` path ambiguous to a reader. No `std` build is affected, and the `no_std` mode is now covered by the same gate list as the others.

All are semantics-preserving rewrites, most of them clippy's own machine-applicable suggestions: `question_mark` / `match`-to-`?` in `oxiz-core/src/qe/mbi.rs`, `oxiz-core/src/tactic/bitblast.rs`, `oxiz-nlsat/src/solver/decide.rs`, `oxiz-theories/src/quantifier_code_tree.rs`, `oxiz-theories/src/euf/ematching.rs`, `oxiz-theories/src/string/solver.rs`, `oxiz-theories/src/string/ground_solver/eval.rs` (2), `oxiz-solver/src/combination/coordinator.rs`, `oxiz-smtcomp/src/loader.rs` and `oxiz-cli/src/model_counter.rs`; `useless_borrows_in_formatting` in `oxiz-sat/src/benchmark.rs` and `oxiz-theories/src/string/replace_operations.rs`; `for_kv_map` in `oxiz-sat/src/preprocessing/variable_elimination.rs` and `oxiz-cli/src/distributed.rs`; `unneeded_wildcard_pattern` in `oxiz-proof/src/coq_enhanced.rs`; `manual_filter` in `oxiz-cli/src/processor.rs`. No behaviour change.
- **The lexer could spin forever on one unlexable byte.** A character that can neither start nor continue a symbol made `read_symbol_chars` consume nothing, so `next_token` minted the same zero-width `Symbol("")` at the same offset for ever — and any scan-to-`Eof`, such as the parser's balanced-paren skip, never terminated. A catch-all arm now raises `unexpected character U+XXXX cannot start a token` (`oxiz-core/src/smtlib/lexer.rs:285-309`). The test that pins it, `test_unlexable_character_at_command_head_still_terminates`, records in its own comment that this is "the shape that hung the wasm build". Also covered end to end by `oxiz-core/tests/parse_script_lexer_errors.rs::parse_script_rejects_an_unlexable_character_instead_of_hanging`.

The real reason the *name* is reserved is that `TermManager` interns every regular-expression term at a built-in `Uninterpreted("RegLan")` sort, so letting a user constant be minted there would hand the Brzozowski-derivative engine an operand it can neither compile nor recognise as foreign. The message now says that and lists the operators that do work (`oxiz-core/src/smtlib/parser/sorts.rs:115`). `rounding_mode_first_class.rs::reglan_stays_reserved_with_an_honest_message` asserts the text no longer contains "not implemented"; `reserving_reglan_does_not_disable_regex_solving` and `audit_parser_fp_bv_ext.rs::reglan_reserved_name_does_not_disable_re_operators` assert the operators still solve.
- **Two wrong axioms in `oxiz-core`'s lightweight theory layer.** `StringAxiom::IndexOfBounds` pinned a lower bound of `0`, but `str.indexof` answers `-1` when the needle does not occur in the haystack at or after the start index, so the axiom ruled out the correct result; the bound is now `-1` (`oxiz-core/src/theories/string.rs`, test `test_indexof_bounds_allow_the_not_found_answer`). And `ArrayTheory::axiom_to_term` unconditionally asserted `mk_eq(array1, array2)` for extensionality; it now returns `Option<TermId>` and builds a quantified premise. **Neither was ever reachable from a `check-sat`**: this is the self-contained layer described under "Added", which no `oxiz-solver` path consults — the string and array theories OxiZ actually solves with live in `oxiz-theories` and were not affected.
- **Every term was retained twice, or three times with `--all-features`.** `TermManager`'s intern cache was a `FxHashMap<(TermKind, SortId), TermId>`, so each term's `TermKind` was stored a second time as part of the map key, and the `arena` feature added a third copy through a `TermArena` that nothing ever read. The cache is now a `hashbrown::HashTable<TermId>` resolving lookups and collisions against `terms[id]`, and the arena write is gone. `hash_term_key` is deliberately bit-identical to the old tuple-key hash so bucket distribution is unchanged, pinned by `test_hash_term_key_matches_the_tuple_key_hash`. Measured on `aarch64-apple-darwin` with `Term` = 152 B, retained bytes per term at 100 B and 1,100 B of payload: **2.00 → 1.00 copies on default features and 3.00 → 1.00 with `--all-features`** (the "before" rows were produced by re-adding the removed copies behind a temporary shim and are not reproducible from this tree). `oxiz-core/tests/intern_single_retention.rs` measures the *slope* under a thread-scoped counting allocator and asserts it stays at or below 1.5, which is why the file holds exactly one test.
- **`cargo deny check bans` passes again.** It had been failing on `oxiz-sat`'s deliberately path-only `oxiz-proof` dev-dependency, which reads as a wildcard version requirement; `allow-wildcard-paths = true` in `deny.toml` scopes the `wildcards = "deny"` rule to published dependencies, where it belongs. The dev-dependency stays path-only for the reason recorded in 0.3.2: a `version` on it survives packaging and would make `cargo publish -p oxiz-sat` try to resolve `oxiz-proof` from crates.io, where it does not yet exist at that point in the publish sequence.
- **The benchmark geomean gate could not fail, and was resolving a path that did not exist.** `bench/regression`'s `--history-dir` resolution was manifest-relative, but the gate is invoked from the repo root as `cargo run -p bench-regression -- --history-dir bench/regression/history`, and under `cargo run -p` `CARGO_MANIFEST_DIR` is the *package* directory — so the path double-prefixed to `bench/regression/bench/regression/history`, and the missing-directory branch soft-passes. Resolution is now CWD-first and both soft-pass messages print the resolved absolute path. **This is honest reporting, not an armed gate**: `bench/regression/history/` still contains only `.gitkeep`, so the run continues to soft-pass — on "no data" rather than on a silently mis-resolved path.
  - **The parity suite structurally cannot support the `<= 1.2x` target that gate carries**, and the reason is in `bench/z3_parity`'s own runners rather than in either solver: `run_oxiz` is an in-process library call while `run_z3` spawns a subprocess — and `find_z3` is called *inside* `run_z3`, probing with `z3 --version`, so every recorded `z3_time` charges at least one extra full process spawn on top of the solve. The floors say the rest: the fastest `z3_time` in the whole current snapshot is 7.4 ms, which is spawn cost rather than solve cost, against a fastest `oxiz_time` of 0.196 ms for a function call. Per this repo's standing rule (README, "Performance"), no solver-vs-solver speed ratio is published from that data, and none is published here; the finding is that the comparison is not measuring what the target assumes, which is a methodology result rather than a regression.
- **Deep-recursion regression tests in twelve files were not testing anything.** They built their "deeply nested" terms with the smart constructors — but `mk_not` folds double negation, so a loop of `mk_not` calls oscillates between depth 0 and 1 and never nests, and `mk_and`/`mk_or` flatten a nested child into the parent, so `acc = mk_or([acc, lit])` produces one wide node rather than a deep tree (and is quadratic besides, since each call re-flattens and re-interns). Every such test now interns the nodes directly through `TermManager::intern_term`, so the chains really are as deep as they claim and the iterative walks they exist to protect are actually exercised — `oxiz-core`'s `ast`, `qe` and `tactic` trees, `oxiz-solver`'s BV encoder, and `oxiz-spacer`'s `walk`/`smt`/`theory`/`translate`/`generalize`/`invariant`. Across 41 files the suite also got cheaper: thread stacks went `1 << 20` → `1 << 17` (1 MiB → 128 KiB) with depths scaled to match (50,000 → 6,250; 60,000 → 7,500; 100,000 → 12,500), preserving the same bytes-per-frame detection sensitivity at an eighth of the cost. `mk_and` and `mk_or` also gained explicit `# Performance` warnings recording the Θ(n²) accumulation shape that made the old tests quadratic.

### Performance

- **The whole SAT trail was cloned on every theory-check iteration** ([#42](https://github.com/cool-japan/oxiz/issues/42)). `solve_with_theory`'s inner loop called `self.trail.assignments().to_vec()` and only then sliced off the suffix it needed — O(trail_len²) over a search. It now reads `&self.trail.assignments()[safe_start..]` in place under a scoped immutable borrow, which is possible because `TheoryCallback::on_assignment` takes `&mut T` (the theory) and never `&mut Solver` (`oxiz-sat/src/solver/search_ext.rs:142`, inside `solve_with_theory` at `:50`). Delivery semantics are unchanged, and the new `oxiz-sat/tests/theory_trail_suffix_delivery_regression.rs` pins the contract the refactor had to preserve (no duplicate delivery within a quiescent stretch; delivery matches the final model).
- **Lazy hyper-binary resolution was measured rather than re-tuned, and the reported blow-up did not reproduce** ([#38](https://github.com/cool-japan/oxiz/issues/38)). `enable_lazy_hyper_binary` **keeps its `true` default and every per-preset value it had** — nothing was flipped; `ConfigPreset::default_config()` merely pins the value explicitly now instead of inheriting it, so a future retuning cannot silently invalidate the tables below. Those tables live in `oxiz-sat/src/solver/config.rs:27-149` and record per-family medians of the on/off conflict ratio: guarded implication chains built specifically to favour the pass 0.98, random 3-SAT n=150 0.97 and n=200 1.00, PHP 1.00, quasigroup QG3 1.06, quasigroup completion at orders 7-15 bit-identical across 30 of 30 pairs. **No family's median reaches 2x in either direction, and the reported ~12x is nowhere in the data.** The pass also does not earn its keep — only 0.02-0.2 % of scans produce a clause, and on one n=150 instance it scanned 211k times against 180k literal dequeues — so the default stays `true` because nothing justifies changing it, not because the pass was shown to be worth having. **Provenance matters here**: the four sweep harnesses are `#[ignore]`d and assert only determinism, verdict-invariance and counter sanity, never a ratio bound, so the tables are prose recorded from one manual run. What *is* machine-checked, by two always-run tests, is that the pass fires when it should and that the binary-implication-graph propagation path no longer enters it. Two new counters (`hyper_binary_attempts`, `hyper_binary_learned`) exist so "neutral here" can be told apart from "never ran" — a distinction this codebase has needed before.
  - **The one code change**: the BIG propagation path no longer calls `check_hyper_binary_resolution` (`oxiz-sat/src/solver/propagate.rs:69-78`), because there is provably a binary clause there and therefore nothing to learn. Conflicts, propagations and decisions are bit-identical on every instance of the sweep while roughly 6-8 % of scans disappear on random 3-SAT, 12-31 % on the guarded chains and 83 % on QG3 order 7. Deliberately not taken: the same filter *inside* the function, because a binary clause can also propagate from the watch lists where the BIG edge may not exist, and that filter was measured to change *which* clauses get learned. Separately, our own docstring said the pass was on "in 6 of the 9 presets"; there are ten presets and it is on in seven, and the wrong number had been quoted back to us verbatim in the issue report — it now names all ten.

## [0.3.2] - 2026-08-05

A soundness release driven by an external report. [#25](https://github.com/cool-japan/oxiz/issues/25) showed that the 168-case in-repo conformance suite this project had been calling "z3 parity" was a regression suite, not a differential-testing result — a random 50-instance QF_UF sample the reporter ran against real z3 found a 34% (17/50) disagreement rate. Per project policy none of the 8 pull requests the reporter subsequently opened (#26-#33) were merged — there is no CLA or uniform contribution-provenance guarantee for this project yet — but every one was read in full for its diagnostic value, and every fix below is an independent, from-scratch reimplementation, verified against a regression test derived from a minimal repro that fails on the pre-fix code. ~270 such tests were added in the process. Issue #25 itself stays open: this release closes the specific bugs it led to, not the underlying claim, since plain QF_UF still isn't represented in the 168-benchmark suite (see "Z3 Parity" below).

### Breaking changes

OxiZ is pre-1.0; per Cargo's SemVer convention a `0.x` minor bump is the breaking-change signal.

- **`NlDispatchResult::Sat` gained a payload**: `Sat` → `Sat(Box<Interpretation>)` (`oxiz-solver/src/solver/check_nlsat.rs`). The nonlinear (QF_NIA/QF_NRA) dispatcher's `sat` verdict now carries the witness model it was checked against instead of an empty unit variant; every match site in the workspace was updated to `Sat(_)`.
- **`SolverConfig` grew new public fields**: `use_vmtf`, `luby_cap`, `enable_stabilize`, `stabilize_base`, `focused_luby_cap`, `rephase_interval`, `reuse_trail`, `enable_failed_literal_probing`, `enable_bve`, `enable_equiv_substitution`, `enable_gate_congruence` (`oxiz-sat`), and `nonlinear_model_search`, `enable_domain_first_branching` (`oxiz-solver`). Both are plain, non-`#[non_exhaustive]` structs, so downstream code constructing one via full struct-literal syntax (without `..Default::default()`) needs updating. All new fields default conservatively (see "New solving capability" below).
- **`VMTF`'s public API was rewritten** (`oxiz-sat/src/vmtf.rs`): the `Option<Var>`-linked-list interface (`select`/`advance`/`reset_queue`) is replaced by a persistent decision cursor (`next_decision`, `on_unassign`, `bump(var, assigned: bool)`). `VMTF` is re-exported from the crate root, so anything constructing or driving it directly needs updating — it went from dead code (`pub use`d but never actually referenced by the solver) to load-bearing; see below.

### Soundness fixes (wrong sat/unsat/model corrected)

- **EUF congruence closure could merge two nodes that were no longer actually congruent.** `propagate` republished a re-canonicalized node's signature via a bare `insert_signature` without evicting its *old* signature-table entry, so a later lookup could hit the stale key and merge in a node that had since diverged — a spurious equality able to turn a `sat` formula `unsat`. Fixed with evict-and-reinsert signature maintenance that cross-checks a hit against the node's own back-reference before trusting it (`oxiz-theories/src/euf/solver/congruence.rs` — `update_sig_entry`, `lookup_live_sig`).
- **Bool/EUF encoding had three independent gaps**, together the root cause of a false-`sat` family the reporter's benchmark tripped over (tracked internally as `firewire_tree`):
  - A non-Bool `(ite c t e)` was interned as an opaque EUF leaf with no link to its conditional-equality meaning — `g(u1)=f(ite c u2 u3)` with `¬c` and `g(u1)≠f(u3)` reported `sat` (forcing the ite to `u3` forces `g(u1)=f(u3)` by congruence, so it isn't). Fixed by hoisting every non-Bool `ite` to a fresh EUF-visible variable plus branch-implications before encoding, deliberately excluding BitVec/Array/String/FP sorts whose own encoders still need to see the raw `ite` (`oxiz-solver/src/solver/encode/bool_euf_encoding.rs` — `eliminate_nonbool_ite`).
  - Bool-sorted `(= b1 b2)` was Tseitin-encoded as an iff gate but, unlike its non-Bool sibling, never registered as an EUF theory constraint — `(= b1 b2)`, `h(b1)=1`, `h(b2)≠1` reported `sat`. Fixed by routing it through the existing `Constraint::Eq` mechanism (`oxiz-solver/src/solver/encode.rs`).
  - A Bool variable or compound Bool term (e.g. `(and p q)`) used as a UF *argument* was never completed for congruence. Fixed by extending the existing `Constraint::BoolApp` completion to argument position, not just Bool-valued application results (`oxiz-solver/src/solver/encode/bool_euf_encoding.rs` — `abstract_compound_bool_args`).
- **Arithmetic⇄EUF combination never shared numeric UF arguments with EUF** — the headline false-`sat` family on QF_UFLIA/QF_UFIDL. A constant or compound numeric UF argument (the `3` in `f(3)`) was folded straight into its linear constraint and never became an arithmetic interface term, so an arithmetic-entailed equality like `x=2, y=x+1 ⊢ y=3` never reached EUF and `f(y)≠f(3)` reported `sat` regardless. Fixed with three cooperating mechanisms: numeric UF arguments are now purified into fresh proxy variables with a `get-value` alias back to the original term (`oxiz-solver/src/solver/encode/numeric_purification.rs`); a bounded per-round "care graph" probes difference-constraint pairs, live EUF disequalities and model-equal argument pairs for entailed (dis)equalities via new Farkas-certificate probes `ArithSolver::entailed_equal_reason`/`entailed_disequal_reason` (`oxiz-theories/src/arithmetic/solver.rs`, wired through `oxiz-solver/src/solver/theory_manager/nelson_oppen.rs`); and, for the non-convex case where no single value is entailed (e.g. `1≤x≤2` with `f(1)=f(2)=a` but neither `x=1` nor `x=2` alone), an explicit `(or (=t lo) … (=t hi))` case-split disjunction is asserted over any small integer domain shared with EUF before conceding `sat` (`oxiz-solver/src/solver/int_case_split.rs`, bounded to spans ≤12 and ≤48 terms per round so as not to reopen the blowup this whole family exists to avoid).
- **A quantified `sat` verdict had no model-verification gate against ground disequalities.** Numeric purification (above) deliberately skips quantifier-trigger functions to protect the MBQI e-matching loop, so a ground disequality routed through such a function could slip past MBQI's own fixpoint check. Fixed with a congruence-based backstop that groups ground applications by function symbol and evaluated argument values and refuses a model that isn't actually a function (`oxiz-solver/src/solver/model_eval.rs` — `quantified_model_refutes_ground_assertions`); the honest answer when it fires is `unknown`, not `unsat` — deriving `unsat` outright would require purifying under binders, which this does not do.
- **NLSAT conflict analysis had three independent bugs** (`oxiz-nlsat/src/solver/`):
  - Resolving in an earlier-decision-level literal during conflict analysis negated the wrong thing — an already-false *clause* literal, which negates to *true* under the trail — producing a learned clause not entailed by the clause database, able to refute a genuinely satisfiable formula. Fixed by reconstructing every resolved-in literal from the trail itself (`conflict.rs` — `analyze_conflict`, `falsified_literal`). Tracked internally as the "1-UIP polarity inversion."
  - A literal the arithmetic theory forced (no clause backing it) had no way to be resolved against and could simply vanish from the learned clause, with the empty result read as outright `Unsat`. Now tracked explicitly (`Learnt::theory_dependent`); the solver answers `Unknown`, never `Unsat`, when an empty clause traces through a dropped theory-forced literal.
  - `ArithDecision::GreedyEmpty` at decision level 0 was treated as proof the whole problem is infeasible, on the reasoning that no boolean choice remained to retract — but the *arithmetic* witness values committed so far were themselves free picks, and the first value offered for an unconstrained variable is always `0`. A bare `x·y=35` (genuinely `sat`) reported `Unsat`. Fixed with a witness ledger that records which region each committed value was drawn from and retries a different point from the same region instead of conceding defeat, bounded to 4096 replacements per `solve()` call (`solver/resample.rs`, new; `interval_set.rs` — `sample_avoiding`/`witness_candidates`).
- **`distinct` over two constants could invert to the wrong answer.** The Tseitin encoder's `TermKind::False` arm pinned its fresh variable false but then returned the *positive* literal as "the literal for false," which evaluates true under that pinning — so `(assert (distinct 5 2))`, which constant-folds through `mk_eq`/`mk_not` to `False`, reported `unsat` instead of `sat`. Fixed to return the negative literal, mirroring the already-correct `True` arm (`oxiz-solver/src/solver/encode.rs`; landed ahead of the rest of this release with 8 regression tests covering constant Int/Bool/BitVec operands and the negated form).
- **`define-fun` call-site arguments could silently vanish.** Expanding a macro call re-derived each formal parameter's term from its bare name via a declared-globals lookup with a `Bool` fallback, instead of reusing the term actually bound while the macro body was parsed — and since terms are hash-consed on `(name, sort)`, a parameter name that didn't happen to collide with a same-sorted global constant produced a *different* `TermId`, so the substitution silently missed every occurrence and the parameter stayed free in the "expanded" body. Affected essentially any non-Bool-parameter `define-fun` call (Bool parameters "worked" only by the coincidence of `Bool` being the fallback sort). Fixed by recording each parameter's exact `TermId` at definition time and substituting those directly, with no name-based re-derivation (`oxiz-core/src/smtlib/parser/{mod,commands,terms}.rs` — `Parser::expand_defined_fun`, new `FunctionMacro` type).
- **A lone `0` clause terminator in a DIMACS file was silently dropped.** The end-of-clause branch only forwarded a clause to the solver `if !current_clause.is_empty()` — but a bare `0` token is DIMACS's spelling of the empty (unconditionally false) clause, so a file like `p cnf 0 1\n0\n` parsed as clause-free and solved `Sat` instead of `Unsat` (`oxiz-sat/src/dimacs.rs` — `DimacsParser::parse_reader`).
- **Pure-literal elimination could contradict a trail-forced fact.** A variable already fixed by a unit fact consumed straight onto the trail is never stored as a retrievable clause, so occurrence-based pure-literal detection couldn't see it — and could judge it "pure" in the polarity that contradicts the trail, dropping clauses only satisfied by the trail's actual value. Two independent implementations of this pass had the identical blind spot; both now take an explicit `fixed: &[bool]` trail-status exclusion set (`oxiz-sat/src/preprocessing_core.rs` — `Preprocessor::pure_literal_elimination`; `oxiz-sat/src/solver/learn.rs` — `inprocess`).
- **On-the-fly hyper-binary resolution could learn an unsound clause, or a sound one DRAT couldn't justify.** Backtracking clears an assignment's value but not its stale decision level, so `check_hyper_binary_resolution` could read an *unassigned* variable's leftover level from before its last backtrack and misjudge it "permanently false at level 0," deriving a clause resting on a premise that was never actually forced; separately, the same pass added its clause to the live database without ever emitting a matching `drat_add`, leaving a gap a later DRAT proof could depend on. Fixed by requiring the reason literal to actually be false before reading its level, and by deferring the entire pass whenever a DRAT or LRAT proof is being traced (`oxiz-sat/src/solver/propagate.rs`).

### New solving capability

- **SAT search engine**, ported in the spirit of CaDiCaL's search loop (`oxiz-sat/src/solver/{decide,mod}.rs`, `vmtf.rs`, `restart_model.rs`): VMTF branching is now actually wired into decisions (previously dead code) alongside VSIDS/CHB/LRB; the search alternates *focused* mode (VMTF decisions, EMA-divergence restarts) with *stable* mode (VSIDS decisions, rare reluctant-doubling restarts and rephasing eligibility); restarts can reuse the longest still-well-ranked decision-trail prefix instead of discarding it outright; best-seen phase snapshots feed periodic rephasing; Luby restart growth is capped rather than left to inflate into a multi-thousand-conflict grind; and learned clauses are tiered `Core`/`Mid`/`Local` from their LBD the moment they're learned. All on by default in every built-in preset.
- **SAT inprocessing toolkit**, opt-in and off by default (`SolverConfig::enable_failed_literal_probing`/`enable_bve`/`enable_equiv_substitution`/`enable_gate_congruence`): failed-literal probing with hyper-binary learning (`solver/probe.rs`), SatELite-style bounded variable elimination (`solver/bve.rs`), equivalent-literal substitution via an iterative — stack-overflow-safe to 50,000+ nodes — Tarjan SCC over the binary-implication graph (`solver/equiv.rs`), and AND/XOR gate-congruence closure feeding extra equivalences to it (`solver/congruence.rs`). All of it refuses to run while a DRAT/LRAT proof is being traced; reintroducing a variable BVE eliminated is a hard `SolverError::EliminatedVariableReintroduction` (every `solve*` call answers `Unknown` until `reset()`) rather than a silent guess, while a variable ELS folded away is instead transparently rewritten to its class representative.
- **LRAT proof production and checking**: online LRAT trace building via transitive antecedent closure over reason clauses (`oxiz-sat/src/solver/lrat_trace.rs`), and a new pure-Rust, forward-only LRAT checker with no external-tool shellout (`oxiz-proof/src/lrat_check.rs` — `check_lrat_proof`, `check_lrat_files`); `oxiz-sat`'s own test suite now verifies proofs it produces against this checker rather than only checking that a file gets written.
- **QF_NIA/QF_NRA nonlinear solving**, on by default (`SolverConfig::nonlinear_model_search`, true in `fast`/`balanced`/`thorough`, only off in `minimal`): an exact, iterative concrete-term evaluator in `BigRational` arithmetic with SMT-LIB Euclidean `div`/`mod` semantics (`oxiz-theories/src/nl_eval.rs`) now double-checks every candidate model before it's trusted; when the core dispatcher can't decide, a stochastic local-search model-repair engine (`nl_repair_search.rs`) and an array/UF grammar-reduction pass (McCarthy read-over-write elimination plus term abstraction, `nl_ground_reduce.rs`) both get a turn — either can only turn `Unknown` into a *checked* `Sat`, never manufacture an `Unsat`. `Int`-sorted `div`/`mod` with a resolvable constant divisor now gets a real polynomial encoding (fresh quotient/remainder variables plus the Euclidean side-constraint) instead of being left untranslated (`oxiz-theories/src/nlsat.rs`).
- **Equality-logic and finite-map preprocessing** (`oxiz-solver/src/solver/`, both unconditional, self-gating on formula shape/size, no config flag): `eq_skeleton.rs` detects formulas built purely from `and`/`or`/`not`/`=` over uninterpreted-sort constants and closes the equality graph into a chordal graph (Bryant & Velev's "Sparse" method) so plain SAT decides it directly, instead of the exponential blowup disjunctive equality chains (e.g. pigeonhole instances) otherwise trigger in the full CDCL(T)/EUF loop — a `Sat` verdict is independently re-verified via a from-scratch union-find before being trusted. `finite_map_ite.rs` recognizes deep `ite(=idx k1, v1, ite(=idx k2, v2, …))` lookup-table spines (as tool-generated QF_LIA tends to produce) and flattens them into one result variable plus flat implications instead of an n-deep per-level mux chain; a new opt-in `SolverConfig::enable_domain_first_branching` gives CDCL a decision-priority queue over such tables' index variables (`solver/branch_priority.rs`).

## [0.3.1] - 2026-07-31

A soundness-and-honesty release. It started as a sweep of the reported GitHub issues and the sweep became the wave: every one of the five reported bugs had the same shape — an input the code did not handle being silently dropped or defaulted instead of raising an error — and searching the workspace for that shape turned up 40+ more of them. Baseline at the start of this wave: `cargo nextest run --workspace --all-features` 8,119 passing (the number recorded at the 0.3.0 release). Confirmed at release time: `cargo nextest run --workspace --all-features` **9,668 passing**, 8 skipped, 0 failed, plus 110 doc-tests (`cargo test --doc --workspace --all-features`). The differential parity suite went **154/168 → 168/168 Correct** — see "Z3 Parity" below for exactly what that does and does not claim.

### Breaking changes

OxiZ is pre-1.0, and per Cargo's SemVer convention a `0.x` minor-version bump is the breaking-change signal. This release has one.

- **`ModelValue::BitVec` widened from `u64` to `num_bigint::BigUint`** (`oxiz-core/src/ast/model.rs`). The variant is now a struct variant, `BitVec { value: BigUint, width: u32 }`, holding the unsigned reading of the bit pattern in `0 .. 2^width`. A `u64` payload could not represent a `(_ BitVec 128)` value at all, so every wide bit-vector answer was truncated on its way out of the solver — this is the API half of the wide-bit-vector soundness fixes below, not a cosmetic widening. Matching new APIs: `ModelValue::from_bitvec_int` (from a possibly-negative or out-of-range `BigInt`), `ModelValue::from_bitvec_bits` (from a `BigUint` bit pattern), `ModelValue::as_bitvec`, `Model::assign_bitvec_big`, and the free function `oxiz_core::ast::model::bitvec_mask`. The existing `Model::assign_bitvec(var, u64, width)` still compiles unchanged and now delegates to `assign_bitvec_big`. Note that `oxiz_core::model::Value::BitVec(u32, u64)` — a different, machine-word-sized type used by the model factory — is untouched.

### Soundness fixes (wrong sat/unsat/model corrected)

- **Reported issues closed** (GitHub [#12](https://github.com/cool-japan/oxiz/issues/12), [#14](https://github.com/cool-japan/oxiz/issues/14), [#17](https://github.com/cool-japan/oxiz/issues/17), [#18](https://github.com/cool-japan/oxiz/issues/18), [#23](https://github.com/cool-japan/oxiz/issues/23)): `mk_distinct` / `mk_not(mk_eq)` over integer arithmetic returning a model that violated the constraint; trivially-unsatisfiable `QF_S` string equalities answering `sat`, with string values missing from the model (`get-value` echoing the constant back, `get-model` giving it sort `Bool`); a spurious `sat` plus a malformed `#x-1` model for trivially-unsatisfiable strict bit-vector comparisons; a stack overflow (SIGABRT, exit 134) on a satisfiable `QF_UF` formula; and `QF_S` reporting `unsat` for a trivially-true implication with a false premise. [#22](https://github.com/cool-japan/oxiz/issues/22) (`QF_AUFLIA` read-over-write) remains open and is *not* claimed fixed.
- **40+ further bugs of the same shape** were found and fixed across the workspace by searching for the pattern rather than the symptom: a `match` with a catch-all that returned the input unchanged, a fallible conversion that fell back to a default, a guard that skipped a write it could not perform. Each site now either handles the case or returns an honest error.
- **Wide (>64-bit) bit-vectors — three separate wrong answers.** (1) `BvSolver::assert_const` pinned only the low 64-bit limb of a constant, so `x = 2^64` at width 128 was encoded as `x = 0` and `x <u 1` came back `sat` on an unsatisfiable query; the primitive is now `assert_const_limbs`, with `assert_const_big` taking a `BigUint`, and every bit below `width` is pinned (`oxiz-theories/src/bv/solver.rs`, `oxiz-solver/src/solver/theory_bv_encode.rs`). (2) `TheoryManager::intern_leaf_for_congruence` keyed its canonical EUF node for a bit-vector literal on the low 64 bits of its value, so `0` and `2^64` at width 128 hashed to the same key and the two distinct constants were merged into one congruence class — and merged as *tautological*, which is exactly what it was not, making `(distinct (g a) (g b))` over them report `unsat`; the key now carries every limb (`oxiz-solver/src/solver/theory_manager.rs`). (3) The model builder read wide fields through a `u64`-typed accessor that returned `None` above 64 bits, so a datatype field was reported unconstrained and filled with a sort default; it now goes through `BvSolver::get_value_big` (`oxiz-solver/src/solver/model_builder.rs`).
- **E-matching instantiation could leave the quantified variable free.** `Substitution::apply`'s walk ended in a `_ => Ok(term)` catch-all, which silently returned bit-vector, string, floating-point, datatype, `Let`, `Match`, `Xor`, `Mod` and `Distinct` nodes *unsubstituted* — an instantiation lemma with the bound variable still free in it, i.e. a wrong formula handed to the solver. The rebuild step is now exhaustive over `TermKind` with no catch-all, so a newly added variant fails to compile rather than being dropped (`oxiz-core/src/ematching/substitution/apply.rs`).
- **Theory-solver state leaked across MBQI rounds**, producing a false `Unsat` on a satisfiable re-check: an explanation read out of a tableau that had since been popped could still name literals belonging to a retracted scope. `Solver::rebase_theory_state` (`oxiz-solver/src/solver/mod.rs`) now backtracks the SAT core to root and resets the EUF, arithmetic and bit-vector solvers together with the derived-reason ledger before each round. The bit-vector reset matters on its own: `BvSolver` accumulates unit facts at its own base level (`assert_const` pinning `x = 5`) that were wired into neither `push` nor `pop`, so a stale `x = 5` could refute a later `(= x 6)`.
- **Cooper quantifier elimination expanded `Xor` and `Ite` four ways per nesting level**, so an *n*-deep chain cost ~2ⁿ calls. The elimination now builds over reference-counted, memoized nodes: each operand pair is expanded once and shared, turning the 2ⁿ blow-up into `O(n)` nodes (`oxiz-core/src/qe/arith/cooper.rs`).
- **The SMT-LIB parser now rejects mixed-width bit-vector binary operands at parse time**, as Z3 does, instead of accepting the term and encoding something else: `Builder::check_bv_binary_widths` (`oxiz-core/src/smtlib/parser/build.rs`) validates both operands against the operator's declared width and returns a `ParseError` on a mismatch.

### Recursion, depth and resource hardening (~400 sites)

- **Every remaining unguarded recursive term walk is now an explicit heap stack.** The conversion covers the SMT-LIB term and sort parsers, the printers, the model evaluator, substitution, and — the ones most easily missed — the derived `Drop`, `Clone` and `PartialEq` implementations on deep public enums (`Pattern`, `ProofStep`, `ArrayTerm`, `Regex`, `AdvancedRegex`, `SeqExpr`, `IntExpr`, `SetSort`, …), where dropping a long chain overflowed the stack in code that never appeared in a backtrace. Depth is now bounded by available memory rather than by the fixed native stack. This is what closes #18.
- **The SMT-LIB term parser is fully iterative** (`oxiz-core/src/smtlib/parser/terms.rs`): an explicit frame stack on the heap, with `MAX_PARSE_DEPTH = 1024` retained as a *resource* bound rather than a stack bound. Operand collection in `build.rs` and sort-alias resolution in `sorts.rs` are iterative for the same reason.
- **Encode-depth memoization.** The Tseitin encoder had no memo, so a shared sub-term of the hash-consed DAG was re-encoded once per path reaching it — exponential on the DAG shape a hash-consing manager naturally produces. `Solver::memoize_encoding` now records each term's encoding and polarity coverage (`oxiz-solver/src/solver/encode.rs`). The same fix landed in `Substitution::apply`, which had the same omission.
- **`ENCODE_DEPTH_LIMIT` measured and lowered from 2000 to 512** (`oxiz-solver/src/solver/mod.rs`). The old bound admitted terms whose encoding died on the native stack; 512 was measured against the deepest of the passes running behind the assert-time gate (`simplify`, `collect_polarities`, Skolemization, `eval_in_model`), with margin. Lowering it is honest in the strict sense: exceeding it routes to `Unknown`, never to a wrong answer, and since the parser already refuses raw nesting past 1024, only the 513..=1024 band of parseable scripts (and arbitrarily deep API-built terms) moves from "encoded" to "honest `Unknown`".
- **Non-ASCII-safe string handling**: byte-index slicing of SMT-LIB input replaced with char-boundary-safe access, so a multi-byte character in a symbol or string literal can no longer panic the lexer.
- **`oxiz-math`: real multivariate polynomial GCD** (`oxiz-math/src/polynomial/gcd_multivariate.rs`). The multivariate path was a stub. It is now the classical *primitive polynomial remainder sequence*: split each operand into content and primitive part with respect to a main variable, recurse on the content over the strictly smaller remaining variable set, and take the primitive-part GCD as the last nonzero element of the pseudo-remainder sequence, re-primitivized at each step to keep coefficients from exploding. The recursion is bounded by the number of distinct variables (`MultivariateGcdConfig::max_recursion_depth`) and the inner loop by `deg_v(b)`, which strictly decreases per pseudo-division. `PolynomialGcd::polynomial_remainder` (`gcd.rs`) keeps its univariate long division but now documents that limitation and points at the multivariate entry points, instead of being silently relied upon for `n`-variate inputs. Reference: Z3's `polynomial.cpp`.
- **Iterative Tarjan SCC** in every copy of it (`oxiz-sat/src/big.rs`, `oxiz-theories/src/set/subset.rs`, `oxiz-wasm/src/optimize/dead_code_elim.rs`), including the component-popping half, which the first pass at the rewrite left recursive.
- **`powi(_, i32::MIN)` no longer recurses forever.** The negative-exponent branch computed `-n` to get a positive exponent; `-i32::MIN` overflows and, with overflow checks off in release, wraps straight back to `i32::MIN` and re-entered the same branch. It now works from the unsigned absolute value (`oxiz-theories/src/fp/interval_arithmetic.rs`).
- **Tier-1 silent fallthroughs replaced by exhaustive matches or honest errors** throughout the crates on the answer path, so an unhandled `TermKind` is a compile error rather than a wrong answer.

### MBQI completeness (the parity push)

The three quantified logics that 0.3.0 shipped below 100% are now at 100%, each by a different mechanism, and each answering `sat` only from a verified model rather than from "no counterexample was found".

- **Exact finite-range expansion of bounded integer quantifiers** (`oxiz-solver/src/solver/encode/finite_expand.rs`). A quantifier whose guard confines its variable to a concrete interval is not really a quantifier: it is shorthand for a finite conjunction (`forall`) or disjunction (`exists`). `expand_finite_quantifiers` performs that expansion at assert time, under the `SolverConfig::finite_expansion_budget` cap, so the ground solver decides the formula directly. This is what lifts `AUFLIA` to 10/10.
- **Skolem witness synthesis, feeding the counterexample-guided instantiation loop** (`oxiz-solver/src/solver/encode/exists_skolem.rs`, `encode/skolem_candidates.rs`, with the refinement loop itself in `oxiz-solver/src/mbqi/counterexample.rs`). An existential asserted at positive polarity on the asserted spine is now Skolemized to a fresh constant — the textbook equisatisfiability rewrite — so the ground solver *searches* for the witness instead of MBQI guessing it from a candidate pool, which was both incomplete (a witness outside the pool was never tried) and dangerous (two guesses for the same existential, asserted together, can be jointly unsatisfiable while the existential is not). Skolem applications are then collected back into the candidate pool so other universals can be instantiated at them, which is what makes cross-quantifier refinement terminate here. This is what lifts `UFLIA` to 20/20.
- **Symbolic model certification over the reals, plus quasi-macro detection** (`oxiz-solver/src/mbqi/model_certify/`, with `model_certify/real/` for the real-sorted case). `certify` answers `true` only after building a concrete, *total* interpretation of every symbol the goal mentions and checking that every assertion — ground and quantified alike — is true under it. That is a model in the ordinary semantic sense, so `sat` follows without appealing to the ground solver's verdict or to a saturation argument; `false` says nothing and leaves the caller's `Unknown` in place. This is what lifts `UFLRA` to 10/10.
- The previously-timing-out quantified benchmarks now finish in about a millisecond — `real_composition.smt2` (`UFLRA`), which spun to the 60-second budget at 0.3.0, is 0.63 ms in the release-time run. Across all 168 benchmarks the OxiZ side of the suite totals ~0.56 s.

### Honesty and state hygiene

- **Stale answers are gone.** The model, the unsat core and the proof are invalidated on every `assert`, `push`, `pop` and `reset` (`Solver::invalidate_results`), so `(get-model)` after a mutation can no longer hand back a model of a formula that is no longer the goal.
- **An unjustified conflict clause now yields `Unknown` instead of a fabricated `Unsat`.** `terms_to_conflict_clause` (`oxiz-solver/src/solver/theory_manager/conflict_clause.rs`) accounts for every reason term explicitly — a live Boolean atom, a theory-derived equality expanded through `DerivedReasons`, or a registered theory tautology — and anything else falls back to negating the whole current assignment. Crucially the fallback is itself fallible: with nothing assigned, the negation of the empty assignment is the *empty clause*, an unconditional top-level refutation, and emitting it would have turned a lost-justification bug into a silent false `Unsat` in release builds where the `debug_assert!`s are compiled out. `None` now travels all the way out and becomes `Unknown`. The same routine also fixes an unsound lemma shape: a reason atom assigned *false* used to contribute `¬var`, a literal that is true under the assignment, where `analyze_theory_conflict` requires every literal of the clause to be false.
- **Solver-owned `DerivedReasons` with absolute scope-depth stamps** (`oxiz-solver/src/solver/theory_manager/derived_reasons.rs`) replace the per-round bookkeeping that could not tell a live explanation from one belonging to a retracted scope.
- **E-matching trigger inference is restricted to uninterpreted heads**, matching Z3's `pattern_inference` (`oxiz-core/src/ematching/trigger.rs`). Proposing an interpreted head as a pattern is what produced a matching loop on `∀x y. x ≤ y ⇒ f(x) ≤ f(y)`-shaped axioms.
- **`(get-unsat-core)` works when `:produce-unsat-cores` is enabled mid-session.** Assertion names are now recorded unconditionally at assert time via `record_assertion_identity` (`oxiz-solver/src/solver/encode.rs`), including on the early-return paths for `true`/`false` constants and for terms refused by the depth guard, so enabling core production after the assertions were made no longer produces an empty core.

### Repeated `(check-sat)` on an unchanged goal

Three independent mechanisms made a caller polling `(check-sat)` in a loop pay for it permanently. All three are fixed, and a fourth change makes the whole question moot in the common case.

- **Hyper-binary-resolution clauses are registered in the learned and assertion ledgers.** `check_hyper_binary_resolution` (`oxiz-sat/src/solver/propagate.rs`) added its on-the-fly binary clause with `add_learned` but wrote to neither `learned_clause_ids` nor the current assertion level's list. An unregistered learned clause is invisible to every mechanism meant to be able to take one back: it was miscounted as an *original* clause by callers computing originals as `num_clauses() - learned_clause_count()`, `forget_learned_since` could not forget it, and `pop` could not retract it — which is not merely accounting, because the resolution discharges the reason clause's remaining literals on the grounds that they are false *at level 0*, and level-0 facts are only level-0 for the current assertion scope. The same site also never computed an LBD, leaving it at the `Clause::learned` default of 0, which `record_usage` reads as "promote straight to the rarely-deleted `Core` tier"; it now computes a real LBD.
- **`Solver::pop` retracts Tseitin-memo entries per entry via the undo journal** (`TrailOp::EncodedTermAdded`) instead of clearing `encoded_terms` wholesale. The wholesale clear assumed the matching `sat.pop()` retracts the definitional clauses of everything in the memo, which holds only for terms first encoded *inside* the popped scope; entries written at an outer level kept their clauses and their SAT variables but lost their memo entry, so the next check re-emitted literal-identical definitional clauses that `add_clause` (no duplicate detection) appended as new original clauses. This was the one genuinely *unbounded* mechanism — one full extra copy per `(push)(pop)` pair, with no plateau. Measured before the fix: one goal went 25 → 361 original clauses over 30 push/pop-and-check cycles; a `mixed-arith` goal 28 → 127 over twelve calls and an `arith-heavy` one 474 → 3267. The journal entry carries the displaced value, so an entry whose polarity coverage was *widened* inside the scope is restored to its narrower pre-scope coverage rather than dropped.
- **MBQI search state is checkpointed and restored around each check** (`oxiz-solver/src/mbqi/integration/search_state.rs`). The line between what belongs to a single search (harvested ground terms, the dedup filter, the blind-instantiation guard, the round counter) and what belongs to the goal (registered quantifiers, `declare-const` candidates, configured limits, cumulative statistics) was in the wrong place, and it went wrong in both directions at once: residue left behind made the next check on an unchanged goal reach *further*, while the accumulated round counter eventually crossed `max_rounds` and made it reach *nothing at all* — MBQI silently stopped instantiating after roughly ten checks on the same goal. `MBQIIntegration::search_checkpoint` and `restore_search_state` now write that line down once.
- **New: a verdict cache** (`oxiz-solver/src/solver/verdict_cache.rs`). Repeating `(check-sat)` on a goal the caller has not touched is now an O(1) cache hit. The guard is a `GoalFingerprint` re-derived from live state on entry to every `check` and compared against the one stored beside the verdict; a mismatch anywhere runs a real search. Invalidation comes from two hooks: `Solver::invalidate_results` on `assert` / `push` / `pop` / `reset`, and `Solver::settings_changed`, which **every** `&mut self` setter in `oxiz-solver/src/solver/config.rs` calls (`set_config`, `set_timeout`, `set_conflict_limit`, `set_decision_limit`, `set_theory_aware_branching`, `set_produce_unsat_cores`, `set_random_seed`, `set_logic`) — and the fingerprint additionally carries the settings by value, so a future setter that forgets is still caught. The distinction the cache draws is deliberate: a setting change drops the cached *verdict* but not the model or core, because those are statements about the assertion stack, which a setting change does not move, whereas `Unknown` in particular is a statement about resource exhaustion under one particular configuration.

#### Soundness fixes (wrong sat/unsat/model corrected)

- **SMT-LIB parser** (`oxiz-core/src/smtlib/parser`): `(div a b)`/`(mod a b)` now route to `mk_div`/`mk_mod` instead of parsing as subtraction; `/`, `abs`, `to_real`, `to_int`, `divisible`, and indexed BV ops (`zero_extend`, `sign_extend`, `rotate_left/right`, `repeat`) get real constructors instead of degrading to Bool-sorted uninterpreted applies; undeclared symbols are now a `ParseError` instead of a silently-fabricated fresh Bool variable; `parse_term` recursion is now depth-guarded; `declare-sort`/`define-fun-rec`/`get-unsat-assumptions` are implemented or honestly rejected instead of silently skipped; `set-option` accepts numeral/decimal/string values instead of coercing to `""`; multi-datatype `declare-datatypes` now parses every constructor group, not just the first.
- **Quantifier tactics** (`oxiz-core/src/tactic/quantifier.rs`): DER's `Forall` rule was logically inverted (eliminated the positive-equality disjunct instead of the disequality disjunct) — now matches `Not(Eq(x,t))` as required; Skolemization now threads one fresh-name counter through the whole goal and tracks polarity (previously reused Skolem names across assertions and ignored `Not`/`Implies` polarity); quantifier instantiation now only fires on positive-polarity top-level `Forall`s instead of any polarity.
- **Boolean/BV rewriting** (`oxiz-core/src/simplification/mod.rs`, `rewrite/bv.rs`): AND/OR absorption and the `Or`-of-`And`s factoring rule no longer discard sibling conjuncts/disjuncts they didn't match; `BvShl`/`BvLshr` on symbolic (non-constant) operands now rebuild the shift term instead of degrading to `Unchanged(lhs)` (which silently turned `x << y` into `x`).
- **`TermManager::substitute`** (`oxiz-core/src/ast/manager/query.rs`): now handles every `TermKind` (previously `Apply`, BV, String, FP, `Xor`, `Distinct`, `Div`/`Mod`, quantifiers, and `Let` were passed through unchanged), and hash-conses on `(TermKind, SortId)` instead of `TermKind` alone (previously same-named variables of different sorts could alias).
- **SAT solver** (`oxiz-sat/src/solver/conflict.rs`, `clause.rs`, `solver/mod.rs`): conflict analysis now resolves reason-clause literals by value instead of assuming the propagated literal sits at index 0 (binary-implication-graph propagation doesn't guarantee that, so the old code could drop a false antecedent and learn an over-strong clause); the anchor decision level for 1-UIP resolution is now the conflict clause's own max level, fixing unsound backtracking on-the-fly-added theory clauses can trigger; clause-slot reuse via the free list was removed (stale watchers could drive bogus unit propagations against a recycled slot's new clause); `solve_with_assumptions` now backtracks to root before evaluating assumptions (previously a leftover model from a prior `solve()` could make a satisfiable assumption set look UNSAT); `add_clause` on 3+-literal clauses now picks the two latest-falsified literals as watches instead of always `lits[0..2]`.
- **NLSAT** (`oxiz-nlsat/src/cad.rs`, `portfolio.rs`, `solver/mod.rs`, `simplify.rs`, `maxsat.rs`, `nia.rs`): Sturm sequences in `cad.rs` are now built from a sign-normalized divisor so root counts are correct when a leading coefficient goes negative (mirrored in `oxiz-math`, see below); `PortfolioSolver` workers now clone the real problem via `snapshot_problem`/`create_configured_solver` instead of solving an empty problem (previously every input answered `Sat`); `solve()` resets trail/decision-level/arithmetic state on re-entry (previously stale state corrupted incremental re-solves); `add_clause` on an empty clause now sets `has_empty_clause` so `solve()` reports `Unsat` instead of dropping the constraint; `max_conflicts` is now honored so `Unknown` is reachable; `simplify_ineq_atom` tracks a `flip_parity` across negative-constant/odd-multiplicity-factor sign flips so `Lt`/`Gt` are not silently inverted; `MaxSatSolver::solve` computes real relaxation-variable costs and models instead of always `Optimal` cost 0; root isolation (`isolate_roots`) bisects with exact rationals to guarantee one root per interval instead of merging roots within a `1e-6` window; the LIA branch-and-bound backtrack in `lia/branching.rs` now uses matched `simplex.push()`/`pop()` instead of `simplex.reset()` (which erased every constraint, not just the current branch's).
- **Math** (`oxiz-math/src/polynomial/extended_ops.rs`, `grobner/buchberger.rs`, `simplex.rs`, `fast_rational.rs`, `rational/mod.rs`): `sturm_sequence` now uses the exact (non-scaling) univariate remainder, fixing wrong root counts on negative-leading-coefficient polynomials; `NraSolver::check_sat` routes leftover linear inequalities through a real Fourier-Motzkin decision procedure and returns `Unknown` (not `Sat`) for genuinely undecided nonlinear leftovers; `reduce()` folds an unreduced remainder back into the result on iteration-cap exhaustion instead of dropping it; `SimplexTableau::add_bound` now repairs a non-basic variable's assignment (Dutertre–de Moura update) so tightened bounds can't be silently missed by `check()`'s pivot loop; `fast_rational` no longer uses `saturating_abs` (which corrupted GCD at `i64::MIN`); number-theory helpers (`factorize`, `euler_totient`) now use Pollard-rho + Miller-Rabin instead of bounded trial division.
- **Quantifier elimination** (`oxiz-core/src/qe/*`): Cooper's method (`qe/arith/cooper.rs`) is now a real construction (boundary/minus-infinity case split, divisibility periods) instead of returning the input formula unchanged while claiming elimination; the omega test's real/dark shadow checks (`qe/arith/omega_test.rs`) are real gap/threshold computations instead of hardcoded stubs; string QE (`qe/string/plugin.rs`) returns `None` (conservative give-up) instead of fabricating `true` for constraints it cannot solve; the placeholder `TermId = usize` array-QE module is no longer re-exported from the crate root (the real, `TermManager`-backed eliminator lives in `oxiz-theories::array::quantifier_elim`).
- **Model evaluation** (`oxiz-core/src/model/evaluator.rs`): out-of-range `BigInt`→`i64`/`u64` conversions now return `EvalResult::Error` instead of silently truncating to an arbitrary in-range value.
- **Theories** (`oxiz-theories`): LIA `ArithSolver::check` now runs branch-and-bound after the LP relaxation instead of reporting `Sat` on a fractional Int assignment; the simplex pivot-limit path reports `Unknown` via `resource_limit_reached()` instead of a fabricated `Sat`; LIA cuts (`lia/cuts.rs`) are now real Gomory/GMI cuts derived from the actual tableau row instead of invalid placeholder inequalities; the BV barrel shifters (`bvshl`/`bvlshr`/`bvashr`, now split into `bv/solver/shifts.rs`) encode an explicit over-shift detector so shift-amount bits above the width still force the correct SMT-LIB fill value; `bvudiv`/`bvurem`/`bvsdiv`/`bvsrem` (now in `bv/solver/division.rs`) compute the quotient product at double width with a zero-forced high half and a non-wrapping adder, closing the `q*b + r` wraparound that previously admitted spurious quotients; `assert_fp_lt`/`assert_fp_le` now encode real IEEE-754 ordering (`encode_fp_lt` plus NaN handling) instead of an ad hoc sign-only check with no ordering constraint at all for `<=`; EUF `UnionFind::find`'s path compression is now trail-recorded so `pop()` restores the exact parent/rank state, and `pop()` correctly truncates proof-forest edges added to pre-existing nodes.
- **Proof / interpolation** (`oxiz-proof`): resolution/unit-propagation/rewrite-rule validators in `rules.rs` now recompute and compare the expected result instead of unconditionally returning `Valid`; Craig interpolation (split into `oxiz-proof/src/craig/{partition,interpolator,...}.rs`) now colors axioms against the caller's explicit A/B `Premise`/`PremiseId` partition instead of coloring everything `A` and returning a trivial `true` interpolant.
- **Spacer (PDR/CHC)** (`oxiz-spacer`): `is_init_reachable` and predecessor-finding now issue real SMT queries (`SmtSolver::check_sat`) against the actual init/transition/POB formulas instead of stub `false`/conjoined-not-disjoined placeholders, so `SpacerResult::Unsafe` is reachable again.
- **Optimization** (`oxiz-opt`): the weighted-MaxSAT stratified path now performs a textbook-exact weighted-to-unweighted reduction (rational weight → unit-weight clause copies) instead of ignoring weights; `unit_propagation` in `preprocess.rs` only treats *hard* unit clauses as facts (previously soft units were folded in too, silently dropping conflicting soft clauses); `optimize_maxsmt`'s weight handling (`context.rs`) is exact-rational (`scaled_weight_int`) instead of coercing every weight to 1.
- **Frontends** (`oxiz-cli`, `oxiz-wasm`): `--count-models` now drives the real solver via bounded blocking-clause enumeration for both exact and approximate modes instead of fabricating a count; `--timeout` is enforced by a wall-clock supervisor process; WASM `minimize`/`maximize`/`assertSoft` are wired into a real `Optimizer` call instead of being silently dropped, and `computeInterpolant` now honestly errors ("not wired up yet") instead of returning partition A's conjunction as a fake interpolant.
